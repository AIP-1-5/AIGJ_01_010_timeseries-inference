## 3. 용어 사전

| 용어 | 쉬운 뜻 | 이 과제에서는 |
| --- | --- | --- |
| 메시지 | 한 번에 보내는 데이터 한 덩어리 | 센서 한 대의 측정 1회분 JSON |
| JSON | `{"이름": 값}` 모양으로 데이터를 적는 글자 형식 | ChirpStack 메시지 본문 |
| 페이로드 (payload) | 메시지 안에 실린 실제 내용 | `{"time": …, "deviceInfo": …, "object": …}` |
| 필드 경로 | JSON 안쪽 값을 점으로 찾아가는 주소 | `deviceInfo.tags.location` = 공간 이름 |
| 토픽 (topic) | `/` 로 단계를 나눈 메시지 주소 | `application/<앱ID>/device/<기기EUI>/event/up` |
| 구독 (subscribe) | "이 토픽 메시지를 보내 주세요"라고 브로커에 등록 | 수집기가 접속할 때마다 구독을 다시 검 |
| 발행 (publish) | 토픽에 메시지를 올리는 것 | ChirpStack 이 발행, 추론 서비스도 발행 기능 있음(꺼 둠) |
| QoS | 메시지 전달 보장 단계 0·1·2 | 우리는 1 (최소 한 번) |
| client_id | 브로커가 접속자를 구분하는 이름 | 기본값 `ts-collector-<호스트이름>` |
| keepalive | "살아 있어요" 신호를 보내는 간격 | 30초 |
| fCnt | LoRaWAN 센서가 메시지마다 붙이는 일련번호 | 같은 번호 = 같은 업링크 → 중복으로 버림 |
| 업링크 (uplink) | 센서 → 서버 방향 메시지 | 토픽 끝이 `event/up` |
| 게이트웨이 | 센서 무선 신호를 받는 안테나 장치 | 2대, 한 대는 시계가 약 4분 55초 빠름 |
| SQLite | 파일 하나짜리 데이터베이스 | `~/ts-collector/data/sensors.db` |
| WAL 모드 | 쓰는 중에도 다른 프로그램이 읽을 수 있게 하는 SQLite 방식 | 수집기가 쓰는 동안 추론 서비스·현황 도구가 읽음 |
| UNIQUE | "이 조합은 한 번만 있을 수 있다"는 DB 규칙 | `(device, space, metric, ts)` |
| systemd | 리눅스의 프로그램 관리자 | 서비스 `ts-collector` |
| 커버율 | 1분 칸 중 데이터가 있는 칸의 비율 | 과제 기준 24시간 95% 이상 |
| NTP | 인터넷으로 컴퓨터 시계를 맞추는 방법 | 재부팅 직후 맞기 전에는 보드 시계가 1970년일 수 있음 |
| epoch 초 | 1970-01-01부터 센 초. 컴퓨터가 시각을 저장하는 방식 | `ts`, `recv_ts` 열 |

## 4. MQTT: 센서 메시지가 오는 길

### 4-1. 왜 MQTT인가
센서는 수십 대이고, 그 값을 원하는 프로그램(우리 수집기, 다른 팀원 수집기, 대시보드)도 여러 개입니다. 센서가 받는 쪽 하나하나에 직접 보내면 연결이 엉킵니다. MQTT는 가운데 **브로커** 하나를 두고, 보내는 쪽은 브로커에 "올리기(발행)"만, 받는 쪽은 브로커에 "구독"만 하면 되게 만든 가벼운 약속입니다. 보내는 쪽과 받는 쪽이 서로를 몰라도 됩니다.

### 4-2. 어떻게 동작하나
1. 수집기가 브로커(`<교육장-MQTT-브로커>:1883`)에 아이디·비밀번호(`.env`)로 접속합니다.
2. 수집기가 토픽 두 개를 구독합니다: `application/+/device/+/event/up`(센서), `xflow/hvacr/+/+/status`(냉난방 상태).
3. ChirpStack 이 센서 메시지를 `application/<앱ID>/device/<기기EUI>/event/up` 에 발행합니다.
4. 브로커는 토픽이 구독 패턴과 맞으면 그 메시지를 수집기에 전달합니다.
5. 수집기는 30초(keepalive)마다 살아 있다는 신호를 주고받습니다. 신호가 끊기면 연결이 끊긴 것으로 봅니다.

### 4-3. 꼭 알아야 할 6가지 설정

| 개념 | 뜻 | 우리 설정과 이유 |
| --- | --- | --- |
| 토픽 와일드카드 `+` | 토픽 **한 단계**를 아무 값이나 받음 | `application/+/device/+/event/up` → 앱ID·기기EUI 가 뭐든 다 받음. 새 센서가 생겨도 구독을 안 바꿔도 됨 |
| 토픽 와일드카드 `#` | 그 뒤 **모든 단계**를 받음 (맨 끝에만) | 예비 규칙 `auto` 의 `topic: "#"` (모든 토픽에 맞는 마지막 규칙) |
| QoS 0 / 1 / 2 | 0 = 한 번 보내고 끝(잃을 수 있음), 1 = 확인받을 때까지 다시 보냄(**중복 가능**), 2 = 정확히 한 번(느림) | `qos: 1`. 잃지 않는 게 중요하고, 중복은 저장할 때 걸러 냄 |
| clean session | true = 접속할 때마다 새 출발, false = 브로커가 구독과 못 받은 메시지를 기억 | `clean_session: false`. 잠깐 끊긴 동안 온 QoS 1 메시지를 재접속 후 받음. 단, `client_id` 가 매번 같아야 함 |
| retain | 브로커가 그 토픽의 **마지막 메시지 1개**를 보관했다가 새 구독자에게 바로 줌 | 수집기는 안 씀. 추론 서비스 발행(`team5b/inference/<공간>`)에 retain 을 걸어 둠 → 대시보드가 켜지자마자 최신값을 받음 |
| LWT (유언 메시지) | 접속할 때 "내가 비정상으로 끊기면 이걸 대신 발행해 줘"라고 맡겨 둠 | 추론 서비스가 `team5b/inference/_status` 에 `{"online": false}` 를 맡겨 둠. 서비스가 죽으면 브로커가 대신 알림 (MQTT 발행은 팀 확인 전이라 지금 꺼 둠) |

> 🎤 **Q. QoS 1을 쓰면 무슨 문제가 생기고 어떻게 해결했나요?**
> QoS 1은 "최소 한 번" 전달이라 재접속 때 같은 메시지가 다시 올 수 있습니다. 그래서 DB에 `(device, space, metric, ts)` UNIQUE 규칙을 걸어 두 번째부터는 저장하지 않고 `duplicates` 카운터만 올립니다. 실제로는 게이트웨이 2대가 같은 업링크를 받는 경우가 더 많았고, 이것은 fCnt(일련번호)로 걸렀습니다. 24시간 동안 중복 1,092건을 제거했습니다.

## 5. ChirpStack 메시지 안에는 무엇이 있나

### 5-1. 실제 메시지 (필요한 부분만, `config.yaml` 주석과 `docs/format_change_example.md` 기준)

```json
{"time": "2026-10-20T07:48:42.752+00:00",
 "deviceInfo": {"devEui": "24e124128c067999", "deviceName": "AM107-067999",
                "tags": {"location": "실습실", "point": "후면 오른쪽"}},
 "object": {"co2": 974, "temperature": 24.3, "humidity": 61.5, "tvoc": 284}}
```

### 5-2. 필드별 뜻

| 필드 | 뜻 | 우리가 쓰는 법 |
| --- | --- | --- |
| `time` | 네트워크 서버·게이트웨이가 무선 신호를 받은 시각(UTC) | 센서 시각 `sensor_ts`. 단, 게이트웨이 시계가 틀릴 수 있음 |
| `deviceInfo.devEui` | 센서 고유 번호 | 토픽의 `{device}` 로 캡처해 `device` 열에 저장 |
| `deviceInfo.deviceName` / `deviceProfileName` | 센서 이름 / 기종(AM103, AM107, EM500-CO2, EM300-TH, EM320-TH, WS302) | 기종마다 `object` 안 항목이 다름 |
| `deviceInfo.tags.location` | 공간 이름 (실습실·사무실·회의실·사무실 밖 …) | `space` 열 |
| `deviceInfo.tags.point` | 공간 안 설치 위치 (전방 좌측, 후면 오른쪽 …) | `point` 열. 한 공간에 센서가 여러 대라 필요 |
| `object` | 측정값 묶음 | `co2`, `temperature`, `humidity` 만 골라 저장 |
| `fCnt` | 센서 메시지 일련번호 | 같은 번호면 중복. 번호가 건너뛰면 센서·무선 쪽 손실 |
| `rxInfo[]` | 이 메시지를 받은 게이트웨이 목록(`gwTime`, `nsTime`) | 게이트웨이 2대가 받으면 2개. `nsTime` 은 일관됨 |
| `deduplicationId` | ChirpStack 이 붙인 중복 구분 번호 | 참고용 (우리는 fCnt 로 거름) |

### 5-3. 실데이터에서 발견한 특징
1. **한 공간에 센서가 여러 대**입니다. 실습실은 9대. 그래서 공간만이 아니라 기기·위치도 저장합니다.
2. **보내는 간격이 센서마다 다릅니다**: 대부분 1분, EM500-CO2 는 2분, 회의실 AM103 과 실습실 전방 우측 AM107 은 10분.
3. **같은 업링크가 두 번** 옵니다(약 3%). 게이트웨이 2대가 받고, 한 대의 시계가 **약 4분 55초(295초) 빠름** → 값·fCnt 는 같은데 `time` 만 5분 차이.
4. '실습실' 태그인데 위치가 '복도'인 센서(18℃·83%)가 있습니다 → 분석(과제 2)에서 별도 공간 '복도'로 분리.

## 6. 설정만으로 형식 대응: `config.yaml` 규칙 엔진

### 6-1. 왜 필요한가
과제 조건: "메시지 형식이 바뀌거나 새 센서가 추가돼도 **프로그램을 고치지 않고 설정만 바꿔** 대응". 코드에 `data["deviceInfo"]["tags"]["location"]` 처럼 박아 두면 형식이 바뀔 때마다 코드를 고치고 다시 배포해야 합니다. 그래서 "어느 토픽의 어느 필드가 공간·항목·시각인지"를 **설정 파일의 규칙(rules)** 으로 뺐습니다.

### 6-2. 어떻게 동작하나
1. 메시지가 오면 파서가 `rules` 를 **위에서부터 차례로** 검사합니다.
2. 토픽이 규칙의 `topic` 패턴과 맞는 **첫 번째 규칙 하나만** 적용합니다. `{device}` 처럼 중괄호로 쓴 칸은 그 값을 꺼내 둡니다.
3. 규칙에 적힌 경로(`space_path`, `timestamp`, `fields_from`, `seq_path`)로 공간·시각·값·일련번호를 꺼냅니다.
4. `metric_aliases` 로 이름을 통일합니다(`temp` → `temperature`, `hum` → `humidity`).
5. `only_metrics` 에 있는 항목만 남깁니다(공용 브로커의 다른 데이터 거르기).
6. 맞는 규칙이 하나도 없으면 버리지 않고 `unmatched` 테이블에 원문을 남깁니다 → 나중에 규칙을 추가할 근거.

| 규칙 이름 | 대상 | 핵심 |
| --- | --- | --- |
| `chirpstack-uplink` | 센서 업링크 | 공간 = `deviceInfo.tags.location`, 값 = `object`, 일련번호 = `fCnt` |
| `hvac-status` | 냉난방 실내기·실외기 | `values.*` → 키(회의실 등)가 공간, `hvac_` 앞말, true/false → 1/0 |
| `auto` | 모르는 형식 (예비) | 숫자 필드를 자동으로 찾아 저장, co2·온도·습도만 |

### 6-3. 형식 변경 대응 예 (산출물 ②, `docs/format_change_example.md`)
가정: 서버가 ChirpStack v3 방식으로 바뀌어 토픽이 `…/rx`, 공간이 `tags.location`(최상위), 시각이 `publishedAt` 으로 바뀜.
1. `config.yaml` 의 `topics` 에 `"application/+/device/+/rx"` 한 줄 추가
2. `rules` 에 `chirpstack-v3-rx` 규칙 1개 추가
3. `sudo systemctl restart ts-collector` 로 설정 다시 읽기
→ **코드 변경 0줄**, 저장 형식(공간·항목·기기·시각·값)이 그대로라 과제 2~8 은 영향 없음. 테스트 `tests/test_parser.py::test_chirpstack_v3_format_change` 가 v4·v3 메시지가 같은 레코드가 되는지 확인합니다.

> 🎤 **Q. "설정만으로 대응한다"는 걸 어떻게 보여 줄 수 있나요?**
> ChirpStack v3 형식으로 바뀌는 상황을 가정하고, `config.yaml` 에 토픽 1줄과 규칙 1개만 추가해 해결했습니다. 파이썬 코드는 한 줄도 고치지 않았고, 테스트로 v4와 v3 메시지가 같은 공간·기기·항목·값·시각으로 저장되는 것을 확인했습니다. 규칙을 깜빡해도 메시지는 `unmatched` 테이블에 원문이 남고, 24시간 동안 규칙 불일치는 0건이었습니다.

## 7. 저장: SQLite에 어떻게, 왜 그렇게 쌓나

### 7-1. 시각을 두 개 저장하는 이유
과제의 "생각해 볼 점": 센서 시각과 받은 시각 중 무엇을 저장해야 하나? 답은 **둘 다**입니다.
- `sensor_ts` = 메시지 안 `time`, `recv_ts` = 수집기가 받은 시각, 분석 기준 `ts` = 센서 시각이 있으면 그것, 없으면 받은 시각.
- 네트워크가 30초 밀렸다가 한꺼번에 와도 센서 시각 기준이면 원래 자리에 들어갑니다. 받은 시각으로만 저장하면 한 1분 칸에 2건, 다음 칸은 0건처럼 보여 가짜 결측·가짜 급변이 생깁니다.

### 7-2. 저장 단계의 4가지 장치

| 장치 | 문제 | 해결 |
| --- | --- | --- |
| WAL 모드 | 수집기가 쓰는 동안 학습·추론·현황 도구가 읽으면 서로 막힘 | `PRAGMA journal_mode=WAL` → 쓰기 1개 + 읽기 여러 개 동시 가능. 추론 서비스는 읽기 전용(`mode=ro`)으로 엶 |
| UNIQUE `(device, space, metric, ts)` | QoS 1 재전송으로 같은 메시지가 다시 옴 | `INSERT OR IGNORE` → 두 번째는 저장 안 하고 `duplicates` +1 |
| fCnt 중복 제거 `(device, metric, seq, seq_hour)` | 게이트웨이 시계 차이로 같은 업링크가 **시각만 5분 다르게** 두 번 옴 → 위 UNIQUE 로 못 거름 | 일련번호(fCnt)가 같으면 중복. 센서가 재가입하면 fCnt 가 0부터 다시 시작할 수 있어 1시간 단위(`seq_hour`)를 같이 키로 씀 |
| 시계 오류 보정 | 게이트웨이 시계가 빨라 센서 시각이 **미래** | 센서 시각이 받은 시각보다 30초 넘게 미래면 받은 시각을 `ts` 로 사용, `clock_skew` 카운터 +1. 원래 값은 `sensor_ts` 에 그대로 |
| 1970년 보정 | 재부팅 직후 NTP 동기화 전엔 보드 시계가 1970년일 수 있음 | 받은 시각이 2020-01-01 이전이면 보드 시계를 믿지 않고 센서 시각 사용, `board_clock_unset` +1 |

### 7-3. 빈 구간 원인을 남기는 `events` 테이블
수집기는 `start`, `connected`, `disconnected`, `stop`, `connect_failed` 를 시각과 함께 기록합니다. 나중에 빈 구간이 생기면 그 시간에 수집기가 꺼져 있었는지(우리 쪽), 연결 중이었는데 안 왔는지(센서·게이트웨이 쪽)를 구분할 수 있습니다.

## 8. 사람 손 없이 다시 살아나기

### 8-1. 세 겹의 안전장치
1. **브로커 재시작·네트워크 끊김** → paho(MQTT 라이브러리)가 1초 → 최대 5초 간격으로 계속 재접속, 다시 붙으면 `on_connect` 에서 **구독을 새로 검**.
2. **짧게 끊긴 동안의 메시지** → `clean_session=false` + QoS 1 → 브로커가 보관했다가 재접속 후 전달.
3. **프로그램이 죽거나 보드가 재부팅** → systemd `Restart=always`(5초 뒤 재시작, 횟수 제한 없음) + `enable`(부팅 시 자동 시작). 첫 접속이 실패해도 `retry_first_connection=True` 로 계속 시도.

## 9. 24시간 수집 현황과 빈 구간 원인

### 9-1. 커버율을 어떻게 세나
- **1분 커버율** = 기간 안 1분 칸 중 데이터가 1건 이상 있는 칸 수 ÷ 전체 1분 칸 수. 같은 공간의 센서 여러 대를 합쳐서 셉니다.
- **기기별 주기 기준 커버율** = 그 센서가 보내는 자기 주기(1·2·10분) 칸 기준. 10분 주기 센서 1대뿐이면 1분 커버율은 원리상 최대 10%이므로 이것으로 판단합니다.
- 진행 중인 1분 칸은 덜 찼으므로 빼고, 15분 이상 비면 '빈 구간'으로 표시해 `events` 와 대조해 원인을 붙입니다.

### 9-3. 빈 구간은 왜 생겼나
1. **10-21 13:12~13:28, 모든 공간 공통 16분** → 수집기 재배포 중 정지(`stop, disconnected`). **우리 쪽 원인**, 24시간의 1.1%.
2. **회의실 19분 공백 2건(10-20 23:03, 10-21 08:43)** → 그때 수집기는 연결 중이었음 → 센서·게이트웨이 쪽 미전송 추정.
3. **회의실 10-21 11:18 19분 공백 1건** → 브로커 연결 끊김, 자동 재접속.
4. 집중회의실 일부 냉난방 항목(현재 온도 등)은 13:06 이후 장비가 해당 값을 보내지 않아 0.1%. 전원(`hvac_power`)은 98.2%.

해석 포인트: **수집기가 아니라 센서 배치가 커버율을 정합니다.** 센서가 여러 대인 실습실은 98% 이상이고, 1대뿐인 공간은 전송 하나만 빠져도 빈칸이 됩니다. 커버율을 올리려면 수집기보다 센서를 늘리거나 주기를 줄여야 합니다.

> 🎤 **Q. 회의실 커버율 9.7%면 과제 실패 아닌가요?**
> 회의실 센서는 1대뿐이고 10분마다 한 번 보내기 때문에 1분 칸 기준으로는 아무리 잘 받아도 최대 10%입니다. 그래서 센서 자기 주기 기준으로 다시 세면 88.8%입니다. 남은 공백 중 2건은 수집기가 연결 중이었는데 안 들어온 센서·게이트웨이 쪽 문제였고, 수집기 쪽 원인은 재배포 16분과 브로커 끊김 1건이었습니다. 보고서에는 미달로 표시하고 원인을 설명했습니다.

class Parser:
    def parse(self, topic: str, payload: bytes) -> Optional[List[Reading]]:
        """맞는 규칙이 없으면 None, 규칙은 맞았지만 값이 없으면 빈 리스트."""

## 예상 질문 모음

**Q. MQTT에서 브로커, 토픽, 구독을 설명해 보세요.**
브로커는 메시지를 받아 나눠 주는 중간 서버(`<교육장-MQTT-브로커>:1883`)입니다. 토픽은 `/` 로 단계를 나눈 메시지 주소이고, 구독은 "이 토픽 메시지를 보내 주세요"라고 브로커에 등록하는 것입니다. 우리 수집기는 `application/+/device/+/event/up` 을 구독해, `+` 자리에 어떤 앱ID·기기EUI 가 와도 모든 센서 업링크를 받습니다.

**Q. clean_session=false 는 왜 썼나요?**
잠깐 끊긴 동안의 메시지를 잃지 않기 위해서입니다. false 로 접속하면 브로커가 우리 구독과 못 받은 QoS 1 메시지를 기억해 두었다가 재접속하면 전달합니다. 실제로 `kill -9` 시험에서 5초 뒤 재시작했을 때 브로커가 보관한 메시지를 받았습니다. 이 기능은 `client_id` 가 매번 같아야 동작합니다.

**Q. 시각은 센서 시각과 받은 시각 중 무엇을 저장했나요?**
둘 다 저장합니다(`sensor_ts`, `recv_ts`). 분석 기준 `ts` 는 센서 시각을 쓰는데, 네트워크가 밀려 한꺼번에 와도 원래 자리에 들어가기 때문입니다. 다만 게이트웨이 시계가 약 5분 빨라 센서 시각이 미래가 되는 경우가 있어서, 받은 시각보다 30초 넘게 미래면 받은 시각으로 바꿉니다.

**Q. 같은 메시지가 두 번 오는 건 어떻게 찾았고 어떻게 막았나요?**
15시간 데이터를 보니 값과 fCnt 는 같은데 `time` 이 정확히 약 295초 차이 나는 쌍이 약 3% 있었습니다. 게이트웨이 2대가 같은 신호를 받았고 한 대의 시계가 빨랐던 것입니다. 시각이 달라 기존 UNIQUE 로는 못 걸러서, `(기기, 항목, fCnt, 받은 시간대)` UNIQUE 인덱스를 추가했습니다. 24시간 동안 중복 1,092건을 제거했습니다.

**Q. 수집과 학습·추론이 같은 DB를 쓰면 문제가 없나요?**
SQLite 기본 모드에서는 읽기와 쓰기가 서로를 막아, 학습이 긴 조회를 하는 동안 수집이 밀릴 수 있습니다. 그래서 WAL 모드로 쓰기 1개와 읽기 여러 개가 동시에 되게 했고, 추론 서비스와 현황 도구는 읽기 전용(`mode=ro`)으로 엽니다. 쓰기는 수집기 하나만 합니다. 학습은 맥북으로 복사한 데이터로 합니다.

**Q. 브로커가 재시작되면 1분 안에 다시 수집되나요?**
네. 로컬 mosquitto 브로커를 껐다 켜는 통합 테스트에서 약 1초 만에 재접속했습니다. paho 가 1초 → 최대 5초 간격으로 계속 재접속하고, 다시 붙으면 `on_connect` 에서 구독을 새로 걸기 때문입니다. 실제 운영 중에도 10-21 11:18 브로커 연결 끊김이 있었는데 자동으로 재접속했습니다.

**Q. 24시간 커버율 95%를 넘었나요? 빠진 구간의 원인은?**
실습실 온도·습도 98.4%, CO₂ 95.1%, 사무실 97.8%로 넘었습니다. 회의실(9.7%, 주기 기준 88.8%)과 사무실 밖(84.2%)은 센서가 1대뿐이라 전송 하나만 빠져도 빈칸이 됩니다. 모든 공간 공통 16분 공백은 수집기 재배포 때문인 우리 쪽 원인(1.1%)이고, 회의실 19분 공백 2건은 수집기가 연결 중이었는데 안 들어온 센서·게이트웨이 쪽 원인입니다.

**Q. 형식이 바뀌면 코드를 고쳐야 하나요?**
아닙니다. 어느 토픽의 어느 필드가 공간·항목·시각인지를 `config.yaml` 의 rules 로 정해 두었습니다. ChirpStack v3 형식 가정 시나리오에서는 토픽 1줄과 규칙 1개만 추가하고 `systemctl restart` 로 해결했고, 코드 변경은 0줄이었습니다. 맞는 규칙이 없어도 메시지는 `unmatched` 테이블에 원문이 남습니다.

**Q. 보드가 재부팅되면 어떻게 되나요?**
systemd 에 `enable` 로 등록해 부팅 때 자동으로 켜지고, `Restart=always` 로 죽어도 5초 뒤 다시 켜집니다. 10-21 18:54 실제 재부팅 때 18:56:21 수집기가 혼자 켜져 7초 뒤 접속·재구독하고 저장을 이어 갔습니다. 재부팅 직후 시계가 아직 안 맞을 때를 대비해 1970년 보정도 넣어 두었습니다.
