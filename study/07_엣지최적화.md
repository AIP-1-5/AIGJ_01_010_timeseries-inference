# ⚡ 7. 과제 7 엣지 최적화: ONNX와 TensorRT

맥북에서 학습한 예측 모델을 작은 보드(Jetson)에서 "최소한의 자원으로, 결과는 똑같이" 돌리는 방법을 정리한 페이지입니다. PyTorch 로 돌리던 모델을 ONNX 라는 공통 형식으로 바꾸자 같은 보드에서 약 280배 빨라졌고, 결과 차이는 0.0001ppm 이었습니다.

> 📖 읽는 순서: 1부(비유·용어 → 왜 필요한가 → 실행 방식 4가지 → 지연·전력 재는 법 → 결과 해석 → TensorRT 를 못 한 이유) → 2부(실제 코드) → 자주 하는 실수 → 예상 질문

# 1부. 처음 보는 사람을 위한 설명

## 1. 한 문장으로 요약하면

> 학습할 때 쓰던 PyTorch 모델을 ONNX 파일로 내보내 보드에서 ONNX Runtime 으로 실행했더니, GRU 1회 추론이 62ms 에서 0.22ms 로 약 280배 빨라졌고 CO₂ 예측값 차이는 0.0001ppm(기준 1ppm 의 1만분의 1)이었습니다. GPU 전용 엔진인 TensorRT(FP16)는 보드에 CUDA·TensorRT 가 설치되어 있지 않고, 팀 공용 보드라 설치하려면 팀 확인이 필요해서 아직 하지 못했습니다.

## 4. 엣지에서 돌려야 하는 이유

1. **데이터가 보드에 있습니다.** 수집기(과제 1)가 보드 안 SQLite 에 센서값을 쌓고, 추론 서비스(과제 8)가 같은 보드에서 매분 읽습니다. 클라우드로 보냈다가 받으면 네트워크가 끊길 때 서비스도 멈춥니다.
2. **교육장 내부망 사정이 있습니다.** 보드는 Tailscale(<보드B-Tailscale-IP>)로 접속하는 현장 장비이고, 결과도 현장(대시보드·냉난방 제어)에서 바로 씁니다.
3. **보드를 혼자 쓰지 않습니다.** 과제 안내에 "이 보드에서는 앞으로 임베딩 모델, 로컬 LLM 이 같이 돈다"고 되어 있습니다. 실제로 측정할 때도 다른 팀원의 로컬 LLM, 수집기, 추론 서비스가 함께 돌고 있었습니다. 그래서 시계열 모델은 **자원을 최소한으로** 써야 합니다.
4. **결과는 똑같아야 합니다.** 빨라졌다고 예측이 달라지면 의미가 없습니다. 그래서 확인 기준이 "변환 후 CO₂ 예측 차이 1ppm 이하"입니다.

## 5. 실행 방식 4가지: 무엇이 다른가

같은 GRU 모델을 네 가지 방법으로 돌릴 수 있습니다.

| 실행 방식 | 비유 | 장점 | 단점 | 이번에 |
| --- | --- | --- | --- | --- |
| PyTorch CPU | 원본 노트 보며 한 줄씩 | 학습 코드 그대로 | 작은 모델은 호출 비용이 계산보다 큼 | ✅ 측정 (62ms) |
| PyTorch GPU | 원본 노트 + 조수들 | 큰 모델은 빠름 | CUDA 필요 | ❌ 보드에 CUDA 없음 |
| ONNX Runtime CPU | 표준 카드로 한 번에 | 그래프 전체 최적화, 설치 쉬움 | GPU 는 별도 설정 | ✅ 측정 (0.22ms) |
| TensorRT FP16 | 이 주방 전용 순서표 + 계량 단순화 | Jetson 에서 가장 빠를 것으로 예상 | CUDA·TensorRT 설치 필요, 변환 오차 확인 필요 | ⏳ 미측정 |

흐름은 다음과 같습니다.

```mermaid
flowchart LR
  A[맥북: PyTorch 로 학습] --> B[export_onnx.py: ONNX 파일로 내보내기]
  B --> C[보드로 복사]
  C --> D[ONNX Runtime CPU 로 실행 - 측정 완료]
  C -.설치 후.-> E[TensorRT FP16 엔진 - 대기]
  D --> F[과제 8 서비스가 매분 사용]
```

**왜 ONNX Runtime 이 이렇게 빠른가** (보고서 해석 그대로)

1. PyTorch 는 연산 하나하나를 파이썬에서 호출합니다. 호출할 때마다 준비·스레드 관리 비용이 듭니다.
2. 우리 모델은 아주 작습니다(입력 24칸 × 몇 개 항목). 그래서 **실제 계산보다 호출 비용이 훨씬 큽니다.**
3. ONNX Runtime 은 모델 전체 그래프를 한 번에 보고 연산을 합쳐(최적화) 한 번에 실행합니다. 호출 비용이 거의 사라집니다.
4. 결과: 62ms → 0.22ms, 약 280배.

## 6. 지연은 이렇게 쟀습니다 (평균, p50, p95, 워밍업)

1. **워밍업 50회**: 처음 몇 번은 메모리 준비·캐시 때문에 느립니다. 이 시간을 섞으면 실제보다 느리게 나오므로 버립니다.
2. **500회 반복**: 한 번만 재면 우연에 휘둘립니다. 500번 재서 통계를 냅니다.
3. **평균·p95 기록**: `bench.py` 는 평균, p95, p99 를 저장합니다. p50(중간값)은 "보통"의 감, p95 는 "20번 중 1번은 이보다 느리다"는 뜻입니다.
4. **왜 p95 가 더 중요한가**: 상시 서비스는 매분 마감이 있습니다. 평균이 빨라도 가끔 크게 늦으면 그 순간 마감을 놓칩니다. 그래서 꼬리 지연(p95)을 봐야 합니다.
5. **측정 조건 기록**: 전력 모드 pmode 0002, 클럭 고정 안 함(기본 DVFS), 워밍업 50회 + 500회, tegrastats 200ms 간격. 과제 확인 기준이 "측정 조건을 함께 기록"이라 반드시 적어야 합니다.

## 7. 전력은 이렇게 쟀습니다 (tegrastats)

1. 측정 구간이 시작될 때 `tegrastats --interval 200` 을 백그라운드로 켭니다.
2. 0.2초마다 나오는 줄에서 `VDD_IN ...mW`(보드 전체 입력 전력), `GR3D_FREQ ..%`(GPU 사용률), `RAM ...`(메모리)을 정규식으로 뽑습니다.
3. 측정이 끝나면 끄고 평균을 냅니다.
4. 비교를 위해 **아무것도 안 할 때(idle)** 5초도 잽니다 → 6,709mW(약 6.7W).

## 8. 우리 결과 숫자와 해석

**GRU 배치 1 (최종 보고서 §7)**

| GRU (배치 1) | 평균 | p95 | 전력 | CO₂ 차이 |
| --- | ---: | ---: | ---: | ---: |
| PyTorch CPU | 62.0ms | 71.7ms | 8.6W | 기준 |
| ONNX Runtime CPU | 0.22ms | 0.22ms | 9.8W | 0.0001ppm |
| TensorRT FP16 | ⏳ | ⏳ | ⏳ | ⏳ |

**세 모델 전체 (task7_report.md)**

| 모델 · 실행 방식 | 평균(배치 1) | p95(배치 1) | 평균(배치 4) | p95(배치 4) | 평균 전력 | 최대 CO₂ 차이 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| GRU · ONNX Runtime CPU | 0.22 | 0.22 | 1.01 | 4.52 | 9,844mW | 0.000109ppm |
| GRU · PyTorch CPU | 61.96 | 71.68 | 39.72 | 49.78 | 8,601mW | - |
| LSTM · ONNX Runtime CPU | 0.48 | 4.26 | 0.64 | 4.32 | 9,607mW | 0.000076ppm |
| LSTM · PyTorch CPU | 23.23 | 26.62 | 41.45 | 47.07 | 8,573mW | - |
| TCN · ONNX Runtime CPU | 0.26 | 0.15 | 0.79 | 4.41 | 9,764mW | 0.000087ppm |
| TCN · PyTorch CPU | 3.44 | 4.25 | 8.53 | 10.23 | 8,707mW | - |

(단위 ms. Chronos-Bolt tiny 는 PyTorch CPU 로 91.9ms, 메모리 약 +68MB)

**해석**

1. **속도**: GRU 기준 62.0 ÷ 0.22 ≈ 280배. 변환만으로 이만큼 빨라진 이유는 5장의 "호출 비용" 때문입니다.
2. **정확도**: ONNX 와 PyTorch 출력 차이가 최대 0.0001ppm 입니다. 기준 1ppm 의 1만분의 1이라 "결과는 똑같다"고 말할 수 있습니다.
3. **p95 가 튀는 이유**: ONNX Runtime 평균은 1ms 미만인데 p95 가 4ms 대로 튀는 경우가 있습니다. 같은 보드의 LLM·수집기가 CPU 를 잡는 순간이 섞였기 때문입니다. 그래도 수 ms 는 1분(60,000ms) 주기에 비하면 아주 작습니다.
4. **TCN vs RNN**: PyTorch 에서는 TCN(3.44ms)이 GRU(62ms)보다 훨씬 빠릅니다. 합성곱은 시간축 24칸을 한 번에 병렬로 계산하고, RNN(GRU/LSTM)은 24칸을 순서대로 계산하기 때문입니다. ONNX Runtime 에서는 셋 다 1ms 미만이라 차이가 작습니다. GPU/TensorRT 에서는 병렬화가 쉬운 TCN 이 더 크게 빨라질 것으로 **예상**합니다(측정 아님).
5. **전력**: 추론 중 약 8.5~10W, 쉴 때 약 6.7W 입니다. ONNX 쪽 전력(9.8W)이 PyTorch(8.6W)보다 조금 높게 나온 것은 짧은 시간에 CPU 를 꽉 채워 쓰기 때문으로 보입니다. 하지만 한 번에 1ms 도 안 걸리므로 매분 한 번 돌리는 서비스 전체로 보면 추가 전력은 무시할 만합니다.
6. **Chronos tiny**: 91.9ms 로 GRU ONNX(0.22ms)의 수백 배입니다. 로컬 LLM(수 GB)과 보드를 나눠 써야 하니 상시 기본 모델은 작은 GRU/TCN + ONNX Runtime 이 맞다고 결론 내렸습니다.

> 🎤 **Q. CPU 로도 1ms 면 충분한데 왜 굳이 변환하나요?**
> 지금은 공간 5개를 매분 한 번이라 CPU 로 충분합니다. 하지만 이 보드에는 앞으로 임베딩 모델과 로컬 LLM 이 같이 올라가서 CPU 가 부족해집니다. 공간이 늘거나 매초 추론이 필요해지면 GPU(TensorRT)로 옮겨 CPU 를 비워 두는 것이 전체 시스템에 유리합니다. 실제로 PyTorch 62ms 를 ONNX 로 바꾸는 것만으로 0.22ms 가 되어 CPU 를 거의 쓰지 않게 됐습니다.

## 9. TensorRT 를 아직 못 한 이유 (솔직하게)

1. 과제 7 의 1번 요구는 "TensorRT 로 변환, FP16 사용"입니다. **이 부분은 하지 못했습니다.**
2. 이유: 보드 B 의 측정 결과 파일(`bench_board_cpu.json`)을 보면 `"cuda": false`, ONNX Runtime 제공자가 `AzureExecutionProvider, CPUExecutionProvider` 뿐입니다. 즉 **CUDA 툴킷과 TensorRT(JetPack 구성요소)가 설치되어 있지 않습니다.** PyTorch 도 CPU 빌드(2.14.1+cpu)입니다.
3. 설치하려면 시스템 패키지를 `sudo` 로 깔아야 하는데, 보드 B 는 **팀 공용 보드**입니다. 다른 팀원의 LLM 작업 환경이 깨질 수 있어 **팀 확인 후 진행**하기로 했습니다.
4. 그래서 PyTorch GPU, ONNX Runtime CUDA, TensorRT FP16 행은 비어 있습니다. `bench.py` 는 이 제공자가 생기면 자동으로 측정하도록 이미 짜여 있습니다(`CUDAExecutionProvider`, `TensorrtExecutionProvider` 가 있으면 돌림).
5. 보고서에는 "설치되면 `tools/build_trt.sh` 로 FP16 엔진을 만든다"고 적혀 있지만, **현재 저장소 `tools/` 에는 이 파일이 아직 없습니다** (bench.py, export_influx.py, export_onnx.py, gap_test.sh 만 있음). 질문을 받으면 "계획만 있고 스크립트는 아직 없다"고 정확히 말해야 합니다.
6. 심화(B)의 INT8 변환도 같은 이유로 하지 않았습니다.

> 🎤 **Q. TensorRT 를 안 했으면 과제 7 은 실패인가요?**
> 확인 기준 두 개 중 "변환 후 CO₂ 차이 1ppm 이하"는 ONNX 변환으로 0.0001ppm 을 확인했고, "측정 조건 기록"도 했습니다. 다만 과제가 요구한 TensorRT FP16 변환과 GPU 측정은 보드에 CUDA·TensorRT 가 없어서 못 했고, 공용 보드라 팀 확인 없이 시스템을 바꿀 수 없었습니다. 그래서 보고서 표에 ⏳ 로 정직하게 남겼고, 설치되면 같은 bench.py 로 바로 채울 수 있게 해 두었습니다.

## 1. PyTorch 모델을 ONNX 로 내보내기 — `inference/tools/export_onnx.py`

```python
meta = json.load(open("models/forecast_meta.json", encoding="utf-8"))  # ← 학습 때 저장한 설정(입력 길이·공간 목록 등)
n_static = len(meta["spaces"])                                          # ← 공간 개수 (공간 원-핫 입력 크기)
for tag in ("GRU", "LSTM", "TCN"):                                      # ← 세 모델 모두 변환
    g = meta["models"][tag]
    m = fc.make_model(g["kind"], g["n_in"], n_static)                   # ← 같은 모양의 빈 모델을 만들고
    m.load_state_dict(torch.load(g["file"]))                            # ← 학습한 가중치를 채움
    m.eval()                                                            # ← 학습 모드 끄기(추론 모드)
    x = (torch.zeros(1, meta["lookback"], g["n_in"]), torch.zeros(1, n_static), torch.zeros(1, 12))  # ← 가짜 입력(모양만 알려 주는 용도)
    out = f"models/forecast_{g['kind']}.onnx"
    torch.onnx.export(m, x, out, input_names=["x_seq", "x_static", "x_future"], output_names=["dz"],  # ← 입력 3개(과거·공간·미래 일정), 출력 1개(변화량)
                      dynamic_axes={k: {0: "b"} for k in ("x_seq", "x_static", "x_future", "dz")}, opset_version=17, dynamo=False)  # ← 배치 크기를 자유롭게(1이든 4든)
    print("saved", out)
```

- `x_seq` = 과거 2시간(5분 × 24칸) 센서값, `x_static` = 어느 공간인지, `x_future` = 앞으로 60분(12칸) 일정 인원, `dz` = 지금 값 대비 변화량 12칸.
- `dynamic_axes` 덕분에 배치 1과 배치 4를 같은 파일로 잴 수 있습니다.

## 2. 지연 측정 — `inference/tools/bench.py`

```python
WARM, ITERS = 50, 500                    # ← 워밍업 50회, 측정 500회

def timeit(fn):
    for _ in range(WARM):                # ← 처음 50번은 버림 (준비 시간 제외)
        fn()
    ts = []
    for _ in range(ITERS):
        t = time.perf_counter()          # ← 아주 정밀한 시계로 시작 시각
        fn()
        ts.append((time.perf_counter() - t) * 1000)   # ← 걸린 시간을 ms 로 저장
    ts = np.array(ts)
    return {"mean_ms": float(ts.mean()), "p95_ms": float(np.percentile(ts, 95)), "p99_ms": float(np.percentile(ts, 99))}  # ← 평균·p95·p99
```

## 예상 질문 모음

**Q. 엣지와 클라우드의 차이는 무엇이고, 왜 엣지를 썼나요?**
클라우드는 인터넷 너머의 큰 서버이고, 엣지는 데이터가 생기는 현장 옆의 작은 컴퓨터입니다. 우리 수집기가 이미 보드 B 에 센서값을 쌓고 있고, 결과도 교육장 대시보드·냉난방 제어가 씁니다. 그래서 보드 안에서 바로 계산하면 네트워크가 끊겨도 서비스가 계속 돕니다.

**Q. ONNX 와 ONNX Runtime 은 같은 건가요?**
아닙니다. ONNX 는 모델을 저장하는 표준 "파일 형식"이고, ONNX Runtime 은 그 파일을 실행하는 "프로그램"입니다. 레시피 카드와 그 카드를 보고 요리하는 요리사의 관계입니다. TensorRT 도 ONNX 파일을 받아 Jetson GPU 전용 엔진으로 바꿀 수 있습니다.

**Q. 왜 280배나 빨라졌나요? 계산 방식이 바뀐 건가요?**
계산 자체는 같아서 결과 차이가 0.0001ppm 입니다. PyTorch 는 연산 하나하나를 파이썬에서 호출해서, 작은 모델에서는 호출·스레드 관리 비용이 실제 계산보다 훨씬 큽니다. ONNX Runtime 은 그래프 전체를 한 번에 최적화해서 실행하므로 그 비용이 거의 없습니다. 그래서 GRU 배치 1이 62.0ms 에서 0.22ms 가 됐습니다.

**Q. FP16 은 무엇이고 왜 쓰라고 했나요?**
숫자 하나를 32비트 대신 16비트로 저장하는 반정밀도입니다. 메모리를 절반만 쓰고 GPU 에서 더 빨리 계산되지만 조금 덜 정밀합니다. 그래서 변환 후 "CO₂ 차이 1ppm 이하"를 확인하라는 기준이 있습니다. 이번에는 TensorRT 가 없어 FP16 은 측정하지 못했고, ONNX Runtime CPU(FP32)로 0.0001ppm 을 확인했습니다.

**Q. p50 과 p95 는 무엇이고, 왜 p95 가 중요하죠?**
500번 잰 시간을 작은 순으로 세웠을 때 가운데(50%)가 p50, 95% 위치가 p95 입니다. p95 는 "20번에 1번은 이보다 느리다"는 뜻입니다. 매분 마감이 있는 상시 서비스는 가끔 늦는 그 순간에 문제가 생기므로 꼬리 지연을 봐야 합니다. 우리 ONNX 결과는 평균 1ms 미만인데 p95 가 4ms 대로 튀었고, 같은 보드의 LLM·수집기 간섭 때문으로 봅니다.

**Q. ONNX 쪽 전력이 PyTorch 보다 높은데 나쁜 것 아닌가요?**
측정 구간 평균은 ONNX 9.8W, PyTorch 8.6W 로 ONNX 가 조금 높습니다. 하지만 ONNX 는 한 번에 0.22ms, PyTorch 는 62ms 라서 같은 일을 하는 데 드는 시간이 280배 차이 납니다. 매분 한 번 돌리면 ONNX 는 거의 바로 끝나고 다시 쉬므로 전체 에너지는 훨씬 적습니다. 쉴 때 보드 전력은 약 6.7W 입니다.

**Q. GRU 와 TCN 중 변환 후 무엇이 더 빨라지나요?**
PyTorch 에서는 TCN 이 3.44ms 로 GRU 62ms 보다 훨씬 빠릅니다. TCN 은 합성곱이라 24칸을 한 번에 병렬 계산하고, GRU 는 24칸을 순서대로 계산하기 때문입니다. ONNX Runtime CPU 에서는 둘 다 1ms 미만(0.22ms, 0.26ms)이라 차이가 작습니다. GPU/TensorRT 에서는 병렬화가 쉬운 TCN 이 더 크게 빨라질 것으로 예상하지만, 아직 측정하지 못했습니다.

**Q. TensorRT 는 언제, 어떻게 할 건가요?**
팀이 공용 보드에 CUDA·TensorRT 설치를 확인해 주면 진행합니다. ONNX 파일은 이미 있으니 TensorRT FP16 엔진으로 변환하고, bench.py 를 다시 돌리면 TensorRT 제공자가 있을 때 자동으로 같은 표에 행이 추가됩니다. 변환 스크립트(build_trt.sh)는 보고서에 계획으로만 적혀 있고 아직 만들지 않았습니다.

**Q. Chronos 는 왜 서비스 기본 모델로 안 썼나요?**
Chronos-Bolt tiny 는 보드에서 한 번에 약 92ms, 메모리 약 68MB 가 더 듭니다. 직접 학습한 GRU ONNX(0.22ms)의 수백 배입니다. 같은 보드에 로컬 LLM 이 올라가야 해서, 상시 기본 모델은 작은 GRU + ONNX Runtime 으로 두고 Chronos 는 데이터가 적은 지금의 예측 후보로 남겼습니다.
