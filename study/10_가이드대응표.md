### 생각해 볼 점
- **시각은 센서가 찍은 것과 수신한 것 중 무엇을 저장해야 하나? 네트워크가 30초 밀렸다가 한꺼번에 도착하면 어떻게 되나?**
  둘 다 저장하고(`sensor_ts`, `recv_ts`), 분석 기준은 센서 시각을 씁니다. 수신 시각으로만 저장하면 30초 밀린 메시지가 한 칸에 몰려 가짜 결측과 가짜 급변이 생기기 때문입니다. 실제로 게이트웨이 하나의 시계가 약 4분 55초 빨라 센서 시각이 미래로 찍히는 경우가 있었고, 이때는 받은 시각으로 보정했습니다(15시간 데이터에서 8,333건).
- **수집과 학습·추론이 같은 저장소를 동시에 쓰면 어떤 문제가 생기나?**
  읽기와 쓰기가 서로 막혀 수집이 밀리고(커버율 하락), 큰 조회가 추론 지연을 늘리며, 학습 도중 데이터가 늘어 같은 쿼리 결과가 달라집니다. 그래서 SQLite WAL 모드(쓰기 1개 + 읽기 여러 개 동시 가능), 쓰기는 수집기 하나만, 학습은 읽기 전용 연결이나 복사본으로 하도록 했습니다.

### 심화(B)
- **저장소 크기 1년 추정 + 다운샘플링·보관 정책** → 했음. 실측 하루 53,184행(행당 426B) → 1년 약 1,941만 행·7.7GB입니다. 처음 이론값 0.7GB보다 10배 큰데, 공간당 센서가 여러 대이고 냉난방 상태 7항목까지 들어오기 때문입니다. 최근 90일은 1분 원본(약 1.9GB), 그 이전은 5분 평균·최소·최대(약 170MB/년)로 줄여 상한을 약 2.1GB로 고정합니다(`collector/tools/estimate_size.py`, `retention.py`).
- **같은 메시지가 두 번 오는 경우(재전송) 찾아서 처리** → 했음. 게이트웨이 2대로 같은 업링크가 약 3% 두 번 들어왔고, 시각이 295초 달라 기존 방식으로는 못 걸렀습니다. LoRa 프레임 번호(fCnt) + 1시간 시간대를 키로 중복을 버리게 바꿨고, 24시간에 1,092건, 8주 데이터에서 95,019건을 걸렀습니다.

- **'어제 같은 시각'이 가장 약한 이유는 무엇인가? 어떤 공간이라면 이 방법이 강할까?**
  요일·결석·환기·휴일에 따라 날마다 사용 모양이 달라 '어제'가 오늘을 잘 설명하지 못하기 때문입니다. 실제로 8주 데이터 60분 CO₂ 오차가 124.0ppm으로 '현재값 유지'(49.0ppm)의 2.5배였고, 회의실은 170.5ppm으로 가장 나빴습니다. 매일 같은 시간표로 같은 인원이 쓰는 고정 수업 강의실이라면 이 방법이 강해질 수 있습니다.
- **고장이 섞인 구간은 학습에 넣어야 할까, 빼야 할까? 평가에서는?**
  예측 모델 학습과 예측 평가에서는 뺍니다(합성은 고장 2시간 전~끝 60분 뒤 제외). 고장 모양을 정상으로 외우면 과제 4의 예측 오차 탐지기가 고장을 못 잡고, 평가가 '틀린 센서값 맞히기'가 되기 때문입니다. 이상 탐지 평가에는 반드시 넣어야 탐지율과 헛경보율을 잴 수 있습니다.

- **회의실 예측이 다른 공간보다 어려운 이유는 무엇인가? 과거 센서값에 없는 정보는 무엇이고, 어디서 얻을 수 있나?**

- **오차가 가장 큰 순간은 언제인가(수업 시작, 점심, 창문 개방)? 그 순간을 맞히는 것이 가능한가?**

- **센서가 정상 범위의 값에서 멈추면 왜 모델이 알아채지 못하나?**

- **과제 3 예측 오차를 이상 점수로 쓰는 탐지기 vs 오토인코더** → 했음. 단독으로 예측 오차 4/15(하루 헛경보 1.0회), 오토인코더 3/15(0.6회)였고, 규칙과 합치면 규칙 + 예측 오차 80%·1.0회가 규칙 + 오토인코더 73.3%·0.6회보다 나았습니다. 검증 주로 다시 고른 '작은 오차가 30분 이어지는지' 기준이 87%·0.43회로 가장 좋았습니다.
- **'영점 틀어짐' 전용 방법(새벽 빈 방 CO₂ ≈ 외기)** → 했음. "밤 빈 방인데 1시간에 10ppm 이상 오르고 480ppm 초과면 센서 탓" 규칙으로 시험 틀어짐 2/2, 정상 데이터 헛경보 0건입니다. 검증으로 기준을 고르자 지연이 307·180분에서 157·135분으로 줄었습니다.

### 생각해 볼 점
- **사람이 막 나간 직후의 빈 방은 왜 '사용중'으로 오판되기 쉬운가? 반대로 막 들어온 직후는?**
  사람이 나가도 CO₂는 환기 속도만큼 천천히 빠져 한동안 '사람이 있던 수준'에 머물기 때문입니다. 퇴실 후 20분 오류율이 15.0%였고, 임계 0.5에서 빈 방 오판의 37%가 퇴실 후 30분 안이었습니다. 반대로 입실 직후는 CO₂가 오르는 데 몇 분이 걸려 '비어있음'으로 오판되며, 입실 후 15분 오류율이 19.5%로 가장 높았습니다.
- **적은 인원이 쓰는 큰 강의실은 센서로 구별할 수 있나? 공간 크기에 따라 무엇이 달라지나?**
  큰 방에 적은 인원이 있으면 부피 대비 CO₂ 발생량이 작아 변화가 작고 구별이 어렵습니다. 작은 회의실(60m³)은 2~3명만 들어와도 15분이면 CO₂가 눈에 띄게 올라, 노쇼 판정 재현율이 100%였습니다. 다만 공간마다 '얼마나 올라야 사람인가' 기준이 달라 회의실을 학습에서 빼면 F1이 95.6 → 85.6으로 떨어졌습니다.
- **환기 경보의 정밀도가 낮으면(헛경보가 많으면) 현장에서 어떤 일이 생기나? 재현율과 정밀도 중 무엇을 우선해야 하나?**
  헛경보가 잦으면 사람들이 경보를 무시하거나 알림을 꺼 버립니다. 그래도 환기를 늦추는 비용(졸림·두통)이 창문을 한 번 더 여는 비용보다 커서 재현율을 우선했고(97.4%), 같은 공간에 15분 안에 다시 울리지 않게 묶어 체감 헛경보를 줄였습니다. 정밀도는 90.1%로 헛경보는 시험 주 21건이었습니다.
- **과제 3의 예측 모델로도 "30분 안에 1,000ppm 초과"를 판단할 수 있다. 분류기를 따로 두는 것이 나은가?**
  예측 모델은 값 전체를 맞히려다 보니 1,000ppm 경계 근처 판단이 둔할 수 있고, 분류기는 '넘느냐 안 넘느냐'에만 집중해 경계를 더 잘 가릅니다. 그래서 서비스에서는 둘 다 계산해 `co2_over_1000_in_min`(예측)과 `ventilation_soon`(분류기)을 함께 냅니다. 두 방식을 같은 시점에서 숫자로 비교한 결과는 보고서에 답이 없습니다.

### 심화(B)
- **한 공간을 학습에서 빼고 사용 여부 추정 시험** → 했음. 실제 재실 정답 F1로 강의실1 99.2 → 97.8, 강의실2 98.5 → 96.7(손해 2점 이하)로 비슷한 공간은 바로 쓸 수 있었습니다. 회의실 95.6 → 85.6, 라운지 89.7 → 85.6은 손해가 커서 1~2주 데이터를 모아 다시 학습해야 합니다.
- **회의실 노쇼·예약 없는 사용 탐지 규칙, 관찰 기록과 대조** → 했음(합성 생성기의 실제 재실과 대조, 시험 예약 294건·노쇼 39건). 노쇼는 "예약 시작 후 15분간 사용 확률 < 0.95"로 재현율 100%·정밀도 80%(F1 88.6), CO₂ 상승 규칙은 F1 66.1이었습니다. 예약 없는 사용은 F1 88.6(재현율 94%·정밀도 84%)이고, 예약 끝난 뒤 30분을 빼야 정밀도가 63% → 84%로 올랐습니다. 실데이터 회의실은 예약 자료가 없어 하지 못했습니다.

- **같은 보드에서 로컬 LLM(W4)과 함께 올려야 한다. 메모리 예산 안에 들어가나?**
  보드 전체 7,485MB에서 오늘 바탕 사용량(약 3.1GB) 기준으로 서비스(170MB) + Chronos(+361MB) + 4-bit 3B LLM을 올리면 0.9~1.6GB만 남아 여유가 적습니다. Chronos를 빼면 나쁜 경우에도 1.2GB 이상 남습니다. 그래서 상시 예측은 torch가 없는 GRU ONNX로 하고, Chronos는 필요할 때만 켜는 예비 기능으로 둡니다(LLM 크기는 일반적인 값이고 실측은 아님).

### 심화(B)
- **공변량을 받는 모델에 온습도·일정 넣어 비교** → 일부 했음. 별도 환경에서 Chronos-2를 돌려 검증 주에 일정 공변량을 넣으면 48.8 → 34.1ppm(−30%)이었고, 온습도는 효과가 없었습니다(50.0). 시험 주와 시간대 공변량은 맥북 메모리 부족으로 중단해 측정하지 못했고, 같은 시점 GRU(18.9)보다는 여전히 나빴습니다.
- **직접 학습 모델 + 사전학습 모델 섞기** → 했음. 합성에서는 검증이 GRU 단독(가중치 1.0)을 골라 14.8ppm 그대로였고, 단순 평균은 24.0으로 오히려 나빴습니다. 실데이터에서는 0.5 평균이 34.4ppm으로 둘 다보다 좋았지만, 두 모델 오차 상관이 0.70이라 이득이 작고 표본(230개 시점)도 작습니다.

### 생각해 볼 점
- **CPU로도 1ms면 충분히 빠른데, 왜 굳이 변환하나? (동시에 올라갈 다른 모델들, 전력, 공간 수 확장)**
  같은 보드에 임베딩 모델·LLM이 함께 돌면 CPU가 모자라고, 공간이 늘면 CPU 시간이 늘기 때문입니다. 실제로 배치 1 → 4에서 CPU는 0.21 → 0.52ms로 늘었지만 GPU는 0.91ms로 거의 그대로였습니다. 다만 지금 규모(공간 5개, 매분 1회)에서는 CPU ONNX가 가장 빨라, 변환의 이득은 공간 수 확장이나 큰 모델(Chronos·LLM)에서 생깁니다.
- **순환 신경망(GRU/LSTM)과 합성곱 모델(TCN) 중 무엇이 변환 후 더 빨라지나? 이유는?**
  TCN입니다. TensorRT에서 TCN은 0.34ms로 GRU·LSTM(0.92ms)보다 2.7배 빨랐고, CPU INT8에서도 TCN만 2.8배 빨라졌습니다(배치 4 0.32 → 0.12ms). 합성곱은 시간축을 한꺼번에 병렬로 계산하지만, GRU·LSTM은 24칸을 순서대로 계산해야 해서 GPU의 병렬성을 못 쓰기 때문입니다.
- **평균 지연보다 '느린 쪽 5%'가 상시 서비스에서 더 중요한 이유는?**
  상시 서비스는 '가끔 늦는 순간'에 마감을 놓치기 때문입니다. 10-21 측정에서 ONNX Runtime 평균은 1ms 미만이었지만 p95가 4.3~4.5ms로 튀었는데, 같은 보드의 다른 팀원 작업(LLM 등)이 CPU를 잡았기 때문입니다. 보드가 한가했던 10-22에는 p95가 평균과 거의 같았습니다.

### 심화(B)
- **INT8 변환, 정확도 손실과 속도 이득 비교** → 했음(ONNX Runtime CPU INT8). 60분 MAE는 0.1~0.4ppm만 나빠졌지만, 정적 INT8은 검증 범위를 벗어난 입력에서 값이 잘려 최대 차이가 179~217ppm(동적 11~37ppm)으로 1ppm 기준을 크게 넘었습니다. 빨라진 것은 TCN 정적뿐이고(2.8배), GRU는 INT8 GRU 커널이 없어 2~3% 느려져 서비스는 FP32를 유지합니다. TensorRT INT8은 이 위험을 이미 확인해 하지 않았습니다.
- **모델 4개 동시 총 메모리, 로컬 LLM과 함께 올릴 조합 제안** → 했음. 한 프로세스 RSS로 ONNX 모델 4개 57MB → + 상태 모델 170MB → + torch·Chronos 531MB이고, 메모리는 대부분 라이브러리(sklearn 약 110MB, torch 약 185MB)였습니다. 권장 조합은 서비스 GRU + 상태 모델(170MB) + 4-bit 3B LLM이고, 7B는 보드를 전용으로 쓰고 Chronos를 뺄 때만 가능합니다.

- **5분 단위로 모으는데, 막 시작된 5분 칸(아직 1~2분치만 있음)을 써도 될까?**
  쓰지 않습니다. 1~2분치 평균은 학습 때 본 '다 찬 5분 칸'과 성격이 다르고, 센서 주기가 1·2·10분이라 일부 센서만으로 공간 평균이 계산되며(실습실 9대 중 몇 대만), 매분 값이 출렁입니다. 그래서 '마지막으로 다 찬 5분 칸'까지만 쓰고, 대가인 최대 5분 지연은 60분 예측에서 문제가 되지 않습니다.
- **같은 고장에 대해 매분 경보를 보내면 어떻게 되나? 경보를 언제 다시 보내야 하나?**
  매분 보내면 한 고장에 한 시간 60통이 와서 운영자가 알림을 끄게 됩니다(알림 피로). 그래서 같은 경보는 1시간에 한 번만 다시 보내도록 했고, 이 덕분에 12시간 동안 경보가 10건(끊김 시험 2번 × 5개 공간)뿐이었습니다. 운영 제안에서는 30분 단위로 묶고 1시간 넘게 이어지면 다시 알리도록 했습니다.
- **다음 주 로컬 LLM이 이 서비스를 '도구'로 쓰려면 결과에 무엇이 더 있어야 할까?**
  기계가 읽는 스키마(OpenAPI나 함수 호출용 JSON 스키마), 값마다 붙은 단위와 기준 시각, 불확실성(예측 구간, 최근 오차)이 필요합니다. 경보 근거와 권장 조치, "회의실 25분 뒤 1,000ppm 초과 예상, 환기 권장" 같은 한 줄 요약도 있어야 합니다. 신선도(`data_age_sec`)와 자기 채점 결과(`monitor`)는 이미 들어 있고, 스키마와 한 줄 요약은 아직 없습니다.

### 심화(B)
- **예측 결과로 환기·냉난방 제어 규칙 설계, 지난 1주 데이터에 적용해 1,000ppm 초과 시간 감소 추정** → 했음(합성 5주차, 물리 모델 재계산). 1,000ppm 초과가 제어 없음 2,738분/주 → 넘으면 환기 288분 → 30분 앞 예측으로 환기 159분으로 줄었습니다(94% 감소). 대신 환기 강화 시간이 1,350 → 2,410분으로 늘어 에너지와의 균형을 봐야 합니다. 실데이터에는 적용하지 않았습니다.
- **서비스가 스스로 성능 감시(60분 뒤 채점, 오차 커지면 알림)** → 했음. 예측을 결과 DB에 저장했다가 실제 값이 들어오면 채점하고, 같은 시점 '현재값 유지'와 비교합니다(`GET /monitor`). 모델 오차가 1.2배를 넘고 5ppm 이상 차이 나면 `model_degraded` 경보를 내며, 리플레이에서 60분 개선율은 사무실 −0.8%, 실습실 7.9%, 회의실 13.2%였습니다. '5ppm 이상' 조건이 없을 때는 조용한 새벽에 25번 헛경보가 났습니다.
