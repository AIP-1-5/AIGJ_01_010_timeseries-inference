## 4. 30초 설명 (외워 둘 것)

> 교육장 센서 데이터를 제 Jetson 보드로 직접 받아서, "60분 뒤 CO₂ 는 얼마일까, 센서나 설비가 고장 났나, 공간을 쓰고 있나"에 답하는 모델을 만들었습니다. 합성 데이터에서는 60분 예측 오차를 현재값 유지보다 63% 줄였지만, 실데이터에서는 9월과 10월의 교실 사용 패턴이 달라서 최근 데이터로 다시 학습했을 때 15% 개선이었습니다. 모델은 ONNX 로 바꿔 보드에서 0.22ms 에 돌고, 매분 자동으로 계산하는 서비스로 12시간 동안 713번 한 번도 실패하지 않았습니다.

## 5. 2분 설명 (흐름대로)

1. **목표**: 현장의 다섯 질문 — 60분 뒤 CO₂·온도는? 고장 났나? 공간을 쓰나? 범용 모델로도 되나? 작은 보드에서 상시로 되나? — 에 숫자로 답하는 것입니다.
2. **수집(과제 1)**: 교육장 MQTT 를 구독하는 수집기를 만들어 보드 B 에 systemd 서비스로 올렸습니다. 24시간 커버율은 실습실 98.4%(CO₂ 95.1%), 사무실 97.8% 입니다. 실제 보드 재부팅(10-21 18:54) 후 2분 만에 자동으로 수집이 다시 시작됐습니다.
3. **실데이터의 함정(과제 1·2)**: 게이트웨이 시계 하나가 약 4분 55초 빨라 같은 측정이 5분 간격으로 두 번 들어왔습니다. LoRa 프레임 번호(fCnt)로 중복을 거르고, 1970년 시각·위치 태그 오류도 전처리에서 고쳤습니다.
4. **예측(과제 3)**: 합성 데이터에서 GRU(일정 포함)가 60분 오차를 40.9 → 15.0ppm, 63% 줄였습니다. 일정 정보를 빼면 20.4ppm 이라 일정이 가장 중요한 입력이었습니다. 실데이터 8주에서는 그대로 학습하면 -2% 였고, 패턴이 바뀐 9/27 이후만 학습하자 15% 개선이었습니다.
5. **이상 탐지(과제 4)**: 규칙은 센서 고장, 예측 오차는 설비 고장을 잡아서 둘을 합쳐 탐지율 80%, 헛경보 하루 1.0회로 기준을 딱 맞췄습니다.
6. **상태(과제 5)**: 환기 선제 경보 재현율 97.4%, 사용 여부 F1 85.8(규칙 79.1)입니다. 내 실데이터에서는 소음 센서를 대리 정답으로 써서 실습실 정확도 89.8%(규칙 73.7%)였습니다.
7. **범용 모델(과제 6)**: Chronos tiny 는 합성에서 현재값 유지보다 못했는데(40.1 vs 38.4), 내 실데이터에선 36.0ppm 으로 가장 좋았습니다.
8. **엣지(과제 7)**: ONNX Runtime 으로 바꾸니 PyTorch CPU 62ms → 0.22ms, 약 280배, 결과 차이 0.0001ppm 입니다. TensorRT 는 보드에 설치되어 있지 않아 아직입니다.
9. **서비스(과제 8)**: 매분 예측·이상·상태를 계산해 HTTP API 로 제공합니다. 12시간 713주기 실패 0, 평균 0.95초, 끊김 경보 정확, 헛경보 0입니다.
10. **배운 것**: 데이터는 직접 봐야 하고, 모델은 과거를 배우므로 다시 학습해야 하고, 정답도 틀릴 수 있습니다.

## 7. 가장 의외였던 발견 5가지 (final_report §9)

1. **같은 측정값이 두 번, 5분 간격으로**
   - 무슨 일: 같은 센서 업링크가 게이트웨이 2대로 두 번 들어왔고(약 3%), 그중 한 게이트웨이 시계가 약 4분 55초 빨랐습니다. 시각만 달라서 "같은 시각 같은 값" 방식의 중복 제거로는 못 걸렀습니다.
   - 해결: LoRa 프레임 번호(fCnt)가 같으면 같은 측정으로 보고 제거하도록 수집기를 고쳤습니다.
   - 쉬운 말: 같은 편지가 우체국 두 곳을 거쳐 왔는데, 한 우체국 소인 날짜가 틀려 다른 편지처럼 보였던 것입니다.
2. **범용 AI(Chronos)가 '그냥 지금 값'보다 못했다** (합성 데이터)
   - 숫자: 60분 CO₂ — 현재값 유지 38.4, Chronos tiny 40.1, 직접 학습 GRU 14.8ppm.
   - 이유: 합성 교실은 수업·쉬는 시간마다 톱니처럼 오르내립니다. 과거 곡선만 보는 범용 모델은 "곧 쉬는 시간"을 모릅니다. 일정 정보 하나가 모델 종류보다 강했습니다.
3. **"정답"도 틀린다**
   - 숫자: 일정으로 만든 '사용 여부' 정답이 직접 관찰한 실제와 89.7% 만 일치했습니다(결석·노쇼·연장).
   - 의미: 모델 점수를 믿기 전에 정답의 품질부터 확인해야 합니다.
4. **합성에선 꼴찌였던 범용 AI가 진짜 교실에선 1등**
   - 숫자: 내 수집기 실데이터 22시간, 60분 CO₂ — 현재값 유지 42.0, 실데이터 학습 GRU 39.3, Chronos tiny 36.0ppm.
   - 이유: 10월 교실은 CO₂ 가 완만하게 변해서 범용 모델의 '추세 이어 그리기'가 잘 맞았습니다. 데이터의 모양에 따라 좋은 모델이 바뀝니다.
5. **합성에서 63% 좋아진 모델이 실데이터에선 0%**
   - 숫자: 8주 전체 학습 GRU 는 -2% (49.0 vs 49.8ppm). 9월 실습실 주 평균 1,281ppm(최대 3,430), 10월 560ppm.
   - 이유: 8~9월(전 기수가 쓰던 기간)과 10월의 교실 사용 패턴이 완전히 달랐습니다. 모델은 '과거의 교실'을 배웠습니다.
   - 해결: 패턴이 바뀐 9/27 이후만 학습하자 15% 개선(33.4 → 28.3ppm). 상시 서비스는 주기적 재학습이 필요합니다.

> 🎤 **Q. 다섯 가지 중 하나만 말한다면?**
> 다섯 번째입니다. 합성 데이터에서 63% 좋아진 모델이 교육장 실데이터에서는 거의 효과가 없었는데, 원인을 찾아보니 9월 실습실 주 평균이 1,281ppm, 10월은 560ppm 으로 사용 패턴이 완전히 달랐습니다. 최근 데이터로만 다시 학습하자 15% 좋아졌습니다. 모델은 과거를 배우므로 상시 서비스는 주기적으로 다시 학습해야 한다는 걸 배웠습니다.

# 2부. 예상 질문과 슬라이드별 대본

## 예상 질문 모음

**Q. 이 과제를 한마디로 하면 무엇인가요?**
교육장 센서 데이터로 "지금 무슨 일이 있고 60분 뒤엔 어떻게 될까"에 답하는 기능을 만들어 Jetson 보드에서 매분 자동으로 운영한 것입니다. 수집기, 예측·이상·상태 모델, ONNX 변환, 상시 서비스까지 보드 한 대에서 돌아갑니다. 12시간 동안 713번 실패 없이 돌았습니다.

**Q. 왜 '현재값 유지'와 비교하나요?**
"60분 뒤도 지금과 같다"는 아무 학습 없이 할 수 있는 가장 단순한 예측입니다. 모델이 이것보다 못하면 쓸 이유가 없습니다. 그래서 과제 기준도 "현재값 유지보다 30% 이상 오차 감소"입니다. 합성에서는 40.9 → 15.0ppm 으로 63% 줄였습니다.

**Q. 실데이터에서는 왜 30% 기준을 못 넘었나요?**
두 가지 이유입니다. 첫째, 실데이터에는 일정 정보가 없습니다. 합성 실험에서 일정을 빼면 오차가 15.0 → 20.4ppm 으로 커질 만큼 일정이 중요했습니다. 둘째, 9월과 10월의 교실 사용 패턴이 달라서 8주 전체로 학습하면 오히려 -2% 였습니다. 최근 패턴(9/27~)으로만 학습하자 15% 개선됐습니다.

**Q. 합성 데이터를 왜 썼나요? 가짜 데이터로 평가한 게 의미가 있나요?**
실데이터에는 수업 일정, 고장 기록, 사용 여부 정답이 없어서, 정답이 필요한 학습·평가는 합성 데이터로 했습니다. 대신 실데이터(InfluxDB 8주, 내 수집기 22시간)로 다시 검증했고, 그 과정에서 합성 모델이 실데이터에서는 77.1ppm 으로 크게 나쁘다는 걸 발견해 서비스 모델을 실데이터 학습 GRU 로 바꿨습니다. 합성 결과만 믿지 않았다는 게 중요한 점입니다.

**Q. 모델을 왜 GRU 로 골랐나요? LSTM·TCN 과 차이는?**
합성 60분 오차가 GRU 15.0, LSTM 14.9, TCN 15.6ppm 으로 1ppm 안쪽 차이였습니다. 심화 실험에서도 같은 과거 길이에서 모델 종류 차이는 1~2ppm 이었고, 과거를 1시간에서 4시간으로 늘리는 게 16.5 → 14.4ppm 으로 더 컸습니다. 모델보다 입력 정보가 중요하다는 결론입니다.

**Q. 이상 탐지에서 규칙과 모델을 왜 둘 다 쓰나요?**
서로 다른 고장을 잡기 때문입니다. 규칙은 튄 값 5/6, 값 고정 3/3, 영점 틀어짐 2/2 처럼 센서 고장을 잡고, 예측 오차는 냉방·환기 정지처럼 값이 정상 범위 안이지만 기대보다 높은 설비 고장을 잡습니다. 규칙만이면 66.7%, 합치면 80.0% 에 헛경보 하루 1.0회입니다.

**Q. 헛경보 하루 1회가 딱 기준이던데, 운이 좋았던 것 아닌가요?**
경계선인 건 맞습니다. 시간대 기대값까지 더하면 탐지율은 86.7% 로 오르지만 헛경보가 2.0회로 기준을 넘어서 채택하지 않았습니다. 그리고 실제 운영 5시간 경보를 직접 확인해 회의 시작 오인 9번, 냉방 중 온도 고정 오인 2번을 찾아 조건을 조정했고, 조정 후에도 합성 기준 80%·1.0회가 유지되는 걸 확인했습니다.

**Q. "정답도 틀린다"는 게 무슨 뜻인가요?**
사용 여부 정답을 수업 일정으로 만들었는데, 6일간 직접 관찰한 것과 비교하니 89.7% 만 일치했습니다. 결석, 노쇼, 수업 연장 때문입니다. 정답이 10% 틀리면 모델이 아무리 좋아도 점수가 그 이상 오르기 어렵습니다. 그래서 내 실데이터에서는 소음 센서를 대리 정답으로 써서 실습실 89.8% vs 규칙 73.7% 를 확인했습니다.

**Q. Chronos 가 합성과 실데이터에서 결과가 뒤집힌 이유는?**
합성 교실은 수업·쉬는 시간마다 톱니처럼 오르내려서, 과거 곡선만 보는 Chronos 는 40.1ppm 으로 현재값 유지(38.4)보다 못했습니다. 10월 실제 교실은 CO₂ 가 완만해서 추세를 이어 그리는 범용 모델이 잘 맞아 36.0ppm 으로 가장 좋았습니다. 데이터 모양에 따라 좋은 모델이 바뀌니, 3주치가 쌓이면 다시 비교할 계획입니다.

**Q. 그럼 서비스에는 왜 Chronos 대신 GRU 를 올렸나요?**
Chronos tiny 는 보드에서 한 번에 약 92ms, 메모리 +68MB 이고 GRU ONNX 는 0.22ms 입니다. 같은 보드에 로컬 LLM 이 올라가야 해서 상시 기본 모델은 가벼운 GRU 로 두었습니다. 보고서에서는 데이터가 적은 지금 Chronos 를 예측 후보로 두고 데이터가 쌓이면 다시 정하자는 의견을 냈습니다.

**Q. ONNX 로 바꾸면 왜 280배나 빨라지나요?**
PyTorch 는 연산 하나하나를 파이썬에서 호출해서, 작은 모델에서는 호출·스레드 관리 비용이 계산보다 훨씬 큽니다. ONNX Runtime 은 그래프 전체를 한 번에 최적화해서 그 비용이 거의 없습니다. 그래서 GRU 가 62ms 에서 0.22ms 가 됐고, 결과 차이는 0.0001ppm 으로 기준 1ppm 의 1만분의 1입니다.

**Q. TensorRT 는 왜 안 했나요?**
보드 B 에 CUDA 툴킷과 TensorRT 가 설치되어 있지 않습니다. 측정 결과에도 `cuda: false`, 실행 제공자는 CPU 뿐으로 나옵니다. 설치하려면 시스템을 바꿔야 하는데 팀 공용 보드라 팀 확인 후 진행하기로 했습니다. bench.py 는 TensorRT 가 생기면 자동으로 측정하도록 짜여 있습니다.

**Q. 서비스가 12시간 무중단이라는데 재부팅 공백은요?**
서비스 주기 713번 중 실패는 0번입니다. 18:54 에 공용 보드가 재부팅돼서 주기 사이가 최대 476초(약 8분) 비었는데, 보드가 꺼진 것이고 부팅 후 systemd 가 자동으로 다시 켰습니다. 재부팅 직후 '데이터 끊김' 경보도 정확히 나왔습니다.

**Q. 학습과 서비스의 전처리가 다르면 어떻게 되나요?**
모델이 학습 때 본 적 없는 분포를 받아 조용히 틀어집니다. 예를 들어 학습은 5분 평균, 서비스는 1분 원본을 쓰면 잡음이 커져 엉뚱한 변화량을 예측합니다. 그래서 둘 다 같은 `tsinf/prep.py` 를 쓰고, 막 시작된 5분 칸도 버립니다.

**Q. 다른 팀은 결과를 어떻게 가져다 쓰나요?**
HTTP 조회 API(보드 B 8080 포트)로 `/spaces`, `/spaces/meeting/forecast?minutes=30`, `/alarms` 등을 부르면 JSON 으로 받습니다. 필드·단위·예시는 `docs/interface.md` 에 정리했습니다. MQTT retain 발행도 설계해 두었지만 공용 브로커라 팀 확인 후 켭니다.

**Q. 다음 주 로컬 LLM 이 이 서비스를 '도구'로 쓰려면 무엇이 더 필요할까요?**
지금도 "회의실 30분 뒤 CO₂"처럼 질문 하나에 숫자 하나로 답하는 API 가 있고, 결과에 단위와 기준 시각, 예측이 불가능할 때의 이유(`reason`)가 들어 있습니다. 추가로 예측의 불확실성(구간), 마지막 갱신 시각의 의미, 경보의 권장 조치를 문장으로 주면 LLM 이 설명하기 쉬워집니다. 권장 조치는 형식 문서의 경보 표에 이미 정리해 두었습니다.

**Q. 예측으로 환기를 제어하면 얼마나 좋아지나요?**
합성 5주차 1주를 물리 모델로 다시 돌린 시뮬레이션입니다. 넘고 나서 환기하는 지금 방식은 1,000ppm 초과가 288분/주, 30분 앞 예측으로 미리 환기하면 159분/주로 거의 절반입니다. 대신 환기 강화가 1,350분에서 2,410분으로 늘어 에너지 손실과 균형을 봐야 합니다.

**Q. 이번 과제에서 가장 크게 배운 것은?**
세 가지입니다. 데이터는 직접 봐야 합니다(중복·시계·위치 오류는 받아 보기 전엔 몰랐습니다). 모델은 과거를 배우므로 패턴이 바뀌면 다시 학습해야 합니다(9월 1,281ppm vs 10월 560ppm). 정답도 틀릴 수 있습니다(일정 기반 정답 89.7% 일치).

**Q. 다음 단계는 무엇인가요?**
수업 시간표를 입력에 연결하고, 최근 2~3주 데이터로 매주 재학습하고(핫 리로드로 무중단 교체 가능), 팀 확인 후 TensorRT(GPU) 변환을 하고, 3주치가 쌓이면 Chronos 와 다시 비교하는 것입니다.

## 슬라이드별 말할 내용

슬라이드 파일은 `deck/project/slides/` 에 있고, 아래 "대본"은 각 슬라이드의 발표자 노트(aside)를 요약·정리한 것입니다. "주의"는 보고서 숫자와 맞춰 말해야 할 부분입니다. 순서는 덱 설정(`deck.json`)의 실제 발표 순서입니다: 1부 무엇을 만들었나(표지~실데이터 문제) → 2부 결과와 가장 의외였던 발견(요약~이상 탐지) → 3부 운영과 다음 단계(엣지·서비스, 마무리).

### 1) 표지 — "교실 CO₂, 60분 앞을 미리 알 수 있을까?"
- 화면: 시계열 데이터 추론 실습 3.2 · 센서 수집부터 Jetson 상시 추론 서비스까지 · 박수연 · team5-b · 2026-10-22
- 대본: 시계열 추론 과제를 맡은 박수연입니다. 교육장 센서 데이터로 "지금 무슨 일이 있고 60분 뒤엔 어떻게 될까"에 답하는 기능을 만들어 Jetson 에서 상시 운영했습니다. 무엇을 만들었고 무엇이 의외였는지 말씀드리겠습니다.

### 2) 목표 — "다섯 가지 질문에 숫자로 답하기"
- 화면: 60분 뒤 CO₂·온도 → 합성 63% · 실데이터 6~15% 개선 / 고장 → 15건 중 80%, 헛경보 하루 1회 / 사용 여부 → 실습실 89.8%(규칙 73.7%) / 범용 모델 → 합성 꼴찌, 진짜 교실 1등 / 작은 보드 → 1회 0.22ms · 매분 운영
- 대본: 현장의 다섯 질문에 숫자로 답하는 과제였습니다. 오른쪽이 결과 요약이고, 네 번째 범용 모델 결과가 가장 의외였습니다.
- 주의: "실데이터 6~15%"는 내 수집기 22시간 6%(41.5 → 39.0), InfluxDB 최근 패턴 재학습 15%(33.4 → 28.3)입니다. 물어보면 둘을 나눠 말합니다.

### 3) 구조 — "센서에서 서비스까지, 보드 한 대에서"
- 화면: 교육장 센서(LoRaWAN → ChirpStack, 1~10분 주기) → 수집기(과제 1, MQTT → SQLite) → 추론 서비스(과제 8, 매분, ONNX Runtime) → 제공(조회 API, MQTT retain, 형식 문서)
- 대본: 센서 값이 MQTT 로 들어오면 수집기가 저장하고, 추론 서비스가 매분 예측·이상·사용 여부를 계산해 내보냅니다. 학습과 서비스가 같은 전처리 코드를 쓰고, 둘 다 systemd 서비스라 재부팅해도 혼자 다시 켜집니다.
- 주의: 화면의 "MQTT (retain)"은 설계·구현은 됐지만 지금은 꺼져 있습니다. 질문이 오면 "공용 브로커라 팀 확인 후 켭니다, 지금은 API 로 제공 중"이라고 답합니다.

### 4) 실데이터 문제 — "실데이터를 받아 보니 생긴 문제 4가지"
- 화면: 같은 값이 두 번(게이트웨이 시계 4분 55초 빠름 → fCnt 로 중복 제거) / 재부팅하면 1970년(부팅 직후 약 1분 시각이 0 → 센서 시각으로 보정) / 위치 태그 오류('실습실' 태그인데 복도 센서 18℃·83% → 별도 공간) / 센서마다 주기가 다름(1·2·10분 → 기기별로 메운 뒤 5분 평균)
- 대본: 실데이터를 직접 받아 보니 교과서에 없는 문제가 나왔습니다. 같은 측정이 두 번 들어왔는데 게이트웨이 시계 하나가 5분 빨라서 생긴 가짜 데이터였습니다. 보드를 재부팅하면 1분 동안 시계가 1970년이 되는 것도 발견했습니다. 모두 수집기와 전처리에서 고쳤습니다.
- 주의: "시계 배터리가 없어"는 슬라이드 표현입니다. 코드 주석은 "재부팅 직후 NTP 동기화 전에는 보드 시계가 1970년"입니다. 질문이 오면 "시간 동기화 전 약 1분"이라고 말하는 편이 안전합니다.

### 5) 요약 — "확인 기준 대비 결과"
- 화면: 1 수집(재접속 1초 · 재부팅 3회 자동 복구 · 실습실 98.4%) / 3 예측(합성 63%↓ · 실데이터 15%↓) / 4 이상(80%, 하루 1.0회, 경계) / 5 상태(재현율 97.4% · 사용 여부 89.8%) / 6 사전학습(구간 ≈80% · 90ms) / 7 엣지(0.0001ppm · 280배) / 8 서비스(713회 실패 0 · 끊김 경보 정확)
- 대본: 합성 데이터에서는 모든 기준을 넘었습니다. 다만 예측은 실데이터에서 15% 개선에 그쳤는데, 그 이유가 이번 과제에서 가장 큰 배움이었습니다.
- 주의: "재부팅 3회"는 10-21 14:03·14:11(과제 4 보고서 운영 점검)과 18:54 입니다. 7번 엣지 칸이 ✓ 이지만 보고서는 "⏳ TensorRT"입니다. "ONNX 기준으로는 충족, TensorRT 는 남았다"고 말합니다. 사용 여부 89.8% 는 내 실데이터(소음 대리 정답) 숫자이고, 합성 기준은 F1 85.8 vs 79.1 입니다.

### 6) 의외의 발견 ① — "합성에서 63% 좋아진 모델이, 진짜 교실에선 0%"
- 화면: 1,281 — 9월 실습실 주 평균 CO₂(최대 3,000ppm 이상, 전 기수) / 560 — 10월 실습실 주 평균(우리 기수) / 패턴이 바뀐 뒤 데이터로 재학습하니 15% 개선, 주기적 재학습 필요
- 대본: 합성에서 63% 좋아진 모델이 실데이터에서는 거의 효과가 없었습니다. 9월은 전 기수가 쓰던 기간으로 평균 1,300ppm 에 최대 3,000ppm 이 넘었고, 10월은 560ppm 정도로 조용했습니다. 모델은 과거의 교실을 배웠고, 최근 데이터로 다시 학습하자 15% 좋아졌습니다.
- 주의: 1,281 은 09-13 주, 그 주 최대는 3,430ppm 입니다. "0%"는 8주 전체 학습 GRU 의 -2%(49.0 vs 49.8)를 말합니다.

### 7) 의외의 발견 ② — "범용 AI(Chronos): 합성에선 꼴찌, 진짜 교실에선 1등"
- 화면: 60분 CO₂ 오차 — 현재값 유지 38.4 / 42.0, GRU 14.8(1등) / 39.3, Chronos tiny 40.1(꼴찌) / 36.0(1등). 예측 구간 적중 ≈80%
- 대본: 학습 없이 바로 쓰는 Chronos 는 합성에서 꼴찌였는데 제가 직접 모은 교실 데이터에서는 1등이었습니다. 합성은 수업·쉬는 시간이 톱니처럼 반복되지만 10월 교실은 완만해서 추세 잇기가 잘 맞았습니다. 데이터가 적은 지금은 Chronos 를 후보로 두고, 쌓이면 다시 비교합니다.
- 주의: 합성은 5주차 1,108개 시점, 실데이터는 내 수집기 22시간 230개 시점입니다. 시점 수가 다르다는 점을 알고 있어야 합니다.

### 8) 이상 탐지 — "규칙과 모델은 서로 다른 고장을 잡는다"
- 화면: 규칙 → 센서 고장(튄 값 5/6, 값 고정 3/3, 영점 틀어짐 2/2, 헛경보 0) / 예측 오차 → 설비 고장(냉방·환기 정지) / 합치면 탐지율 80%, 헛경보 하루 1.0회 / 실운영 점검: 회의 시작 오인 9번, 온도 고정 오인 2번 → 30분 연속·2시간 조건으로 조정
- 대본: 규칙은 튄 값·값 고정 같은 센서 고장을, 모델의 예측 오차는 냉방·환기 정지 같은 설비 고장을 잡았습니다. 실제 운영 중 낸 경보도 직접 확인해서 오인한 경우를 찾아 조정했습니다.

### 9) 엣지·서비스 — "작은 보드에서 빠르고 끊김 없이"
- 화면: 280× (PyTorch CPU 62ms → ONNX Runtime 0.22ms, 차이 0.0001ppm) / 0.9초 (매분 5개 공간 전체 계산, 12시간 713회 실패 0, 헛경보 0, 재부팅도 2분 만에 자동 복구) / 예측형 환기 제어: 1,000ppm 초과 288 → 159분/주
- 대본: ONNX Runtime 으로 바꾸자 280배 빨라졌고 결과 차이는 0.0001ppm 이었습니다. 서비스는 매분 1초 안에 다섯 공간을 계산하고 12시간 동안 713번 한 번도 실패하지 않았습니다. 보드가 재부팅됐을 때도 저절로 복구됐습니다. 예측으로 미리 환기하면 초과 시간이 지금 방식보다 절반 가까이 줄어든다는 시뮬레이션 결과도 얻었습니다.
- 주의: 보고서 평균은 0.95초입니다("약 1초"라고 말하면 안전). "2분 만에 복구"는 **수집기** 기준(18:56:21 자동 시작)이고, 서비스 주기 사이 최대 공백은 476초(약 8분)입니다. 제어 시뮬레이션은 합성 데이터 위 추정이고 환기 시간은 1,350 → 2,410분/주로 늘어난다는 점도 함께 말합니다. TensorRT 는 미완료라는 점을 질문 전에 한마디 넣어도 좋습니다.

### 10) 마무리 — "배운 것과 다음 단계"
- 화면: 데이터를 직접 봐야 한다 / 모델은 과거를 배운다 / 정답도 틀린다(89.7%) / 다음: 수업 시간표 연결 · 매주 재학습 · TensorRT(GPU) 변환 · 3주치 쌓이면 Chronos 와 재비교
- 대본: 세 가지를 배웠습니다. 데이터는 직접 봐야 한다, 모델은 과거를 배우므로 패턴이 바뀌면 다시 학습해야 한다, 정답 자체도 틀릴 수 있다. 다음으로 시간표를 입력에 연결하고, 매주 재학습하고, GPU 변환을 해 보겠습니다. 감사합니다.
