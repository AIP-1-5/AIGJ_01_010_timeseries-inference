# 과제 1 — 생각해 볼 점 답변 (보고서용 초안)

## Q1. 시각은 센서가 찍은 것과 수신한 것 중 무엇을 저장해야 하나? 30초 밀렸다가 한꺼번에 오면?

**둘 다 저장한다.** `readings` 테이블에 `sensor_ts`(센서 시각)와 `recv_ts`(수신 시각)를 모두 남기고,
분석 기준 시각 `ts` 는 센서 시각이 있으면 센서 시각, 없으면 수신 시각을 쓴다.

- 네트워크가 30초 밀렸다가 한꺼번에 도착하면, 수신 시각으로 저장할 경우 여러 건이 같은 시각 근처로 몰리고
  원래 1분 간격이 무너진다 → 1분 칸에 2건, 다음 칸은 0건처럼 보여 **가짜 결측과 가짜 급변**이 생긴다.
- 센서 시각을 기준으로 하면 늦게 와도 원래 자리에 들어간다.
- 두 시각의 차이(`recv_ts - sensor_ts`)는 그 자체로 **네트워크 지연 지표**가 되어, 결측 원인 설명(과제 1 산출물)과
  이상 탐지(게이트웨이 문제)에 쓸 수 있다.
- 단, 센서 시계가 틀어져 있을 수 있으므로(시계 드리프트) 차이가 비정상적으로 크면(예: 10분 이상) 수신 시각을 의심 신호로 본다.

**실제 데이터에서 확인한 점 (2026-10-20)**: 교육장 센서는 LoRaWAN → ChirpStack 을 거쳐 오며, 페이로드의 `time` 은
센서 자체 시계가 아니라 **네트워크 서버가 무선 신호를 받은 시각**이다. LoRa 센서는 시계가 없거나 부정확한 경우가 많아
이 값이 사실상 '측정 시각'에 가장 가깝다. MQTT 브로커 → 수집기 구간이 밀려도 `time` 은 변하지 않으므로 `sensor_ts` 로 쓴다.
또 센서마다 주기가 1~2분으로 다르고 한 공간에 여러 대가 있어, 공간 단위로 합치면 1분 칸이 더 많이 채워진다.

## Q2. 수집과 학습·추론이 같은 저장소를 동시에 쓰면 어떤 문제가 생기나?

- **잠금 충돌**: SQLite 기본 모드에서는 읽기와 쓰기가 서로를 막는다. 학습이 긴 쿼리를 돌리는 동안 수집기가 못 쓰면
  메시지를 놓치거나 지연된다 → **커버율 하락**.
- **성능 간섭**: 큰 조회가 디스크·CPU 를 차지해 수집이 느려진다. 반대로 수집 쓰기가 추론 지연(p95)을 늘린다.
- **일관성**: 학습 도중 데이터가 계속 추가되면 같은 쿼리를 두 번 돌려도 결과가 달라진다(재현성 문제).
- **사고 위험**: 학습 코드의 실수(DELETE, 스키마 변경)가 원본 데이터를 망칠 수 있다.

대응
- SQLite **WAL 모드**: 쓰기 1개와 읽기 여러 개가 동시에 가능 (이 수집기에서 적용).
- 학습·분석은 **읽기 전용 연결**(`mode=ro`)로 접근, 또는 하루 한 번 **스냅샷 복사본**으로 학습해 재현성 확보.
- 쓰기는 수집기 하나만 (단일 작성자 원칙).
- 규모가 커지면 시계열 DB(InfluxDB 등)로 분리.

## 심화 B-1. 1년 뒤 저장소 크기와 보관 정책
`tools/estimate_size.py` 결과를 붙인다. 이론값: 4공간 × 3항목 × 1440분 × 365일 ≈ **630만 행/년**, 행당 약 110B → **약 0.7GB/년**.

## 심화 B-2. 같은 메시지가 두 번 오는 경우

**실제로 발견한 문제 (2026-10-21)**: 15시간 데이터를 보니 같은 업링크가 **두 번** 들어오는 경우가 약 3% 있었다.
두 메시지는 값·프레임번호(fCnt)는 같은데 `time` 이 **정확히 약 295초(4분 55초)** 차이 났다 → 게이트웨이가 2대이고,
그중 하나의 시계가 약 5분 빠르다고 추정(사무실·회의실 쪽 센서는 대부분 빠른 시계로 찍힘).
- 기존 `(기기, 항목, 시각)` 기준 중복 제거로는 시각이 달라 **못 거른다** → 같은 값이 5분 간격으로 두 번 저장되는 가짜 데이터.
- 대응: LoRaWAN 프레임 번호 `fCnt` 를 저장하고 `(기기, 항목, fCnt, 받은 시간대)` 에 UNIQUE → 두 번째는 버림.
  (fCnt 는 센서가 재가입하면 0부터 다시 시작할 수 있어 1시간 단위 시간대를 함께 키로 씀)
- 시계 문제: 센서 시각이 받은 시각보다 30초 넘게 **미래**면 시계 오류로 보고 받은 시각을 분석 기준 `ts` 로 쓴다
  (원래 값은 `sensor_ts` 에 그대로 남김, `clock_skew` 카운터로 집계).

QoS 1 은 "최소 한 번" 전달이라 재접속 때 같은 메시지가 다시 올 수 있다.
`(공간, 항목, 시각)` 에 UNIQUE 제약을 걸어 **두 번째부터는 저장하지 않고 `duplicates` 카운터만 올린다**.
현황 도구에 "중복 제거 N건"으로 보인다. (센서 시각이 없는 형식에서는 수신 시각이 달라 중복을 구분할 수 없다는 한계가 있음 → 센서 시각을 보내도록 요청하는 근거)
