## 1. INT8 양자화 방법
| 방식 | 하는 일 | 보정 데이터 |
|:--|:--|:--|
| 동적 (quantize_dynamic, 가중치 QInt8) | 가중치를 미리 INT8 로 저장, 활성값 범위는 실행할 때마다 계산 | 필요 없음 |
| 정적 (quantize_static, QDQ, 채널별, MinMax) | 가중치·활성값 모두 INT8 범위를 미리 정해 둠 | **검증 주(4주차) 샘플 512개** — 시험 주는 쓰지 않음 |

실제로 INT8 로 바뀐 연산 (ONNX 그래프 확인):
| 모델 | 동적 | 정적 |
|:--|:--|:--|
| GRU | 끝단 Linear 2개만 (MatMulInteger). **GRU 연산 자체는 FP32 그대로** — ORT 에 INT8 GRU 커널이 없음 | 끝단 Linear 앞뒤에 Q/DQ 만. GRU 는 FP32 |
| LSTM | **LSTM 도 INT8** (DynamicQuantizeLSTM) + 끝단 Linear | 끝단 Linear 앞뒤 Q/DQ 만. LSTM 은 FP32 |
| TCN | Conv 4개 + Linear 2개 (ConvInteger). QInt8 가중치는 CPU EP 에 ConvInteger 커널이 없어 실행 불가 → **QUInt8 로 바꿔서** 만듦 | Conv 4개 + Linear 2개 모두 Q/DQ (CPU EP 가 QLinearConv 로 합침) |

- 왜: 모델이 작고(파라미터 약 4~6만 개) RNN 은 순서대로 계산하는 연산이라 ORT 가 INT8 로 바꿀 수 있는 부분이 제한적이다.
- 그래서: GRU 는 INT8 로 바꿔도 사실상 FP32 와 같은 모델이다. INT8 효과를 보려면 LSTM(동적)이나 TCN(정적)이어야 한다.

## 2. 정확도 — 60분 CO₂ MAE (ppm, 맥에서 측정)
| 모델 | 방식 | 파일 크기 KB | 검증 MAE | **시험 MAE** | 시험 MAE 변화 | FP32 대비 평균 차이 | p99 차이 | **최대 차이** | 10ppm 넘게 달라진 샘플 |
|:--|:--|--:|--:|--:|--:|--:|--:|--:|--:|
| GRU | FP32 | 184 | 18.68 | 14.96 | - | - | - | - | - |
| GRU | INT8 동적 | 167 | 18.95 | 15.23 | +0.27 | 0.81 | 5.4 | 10.6 | 0.1% |
| GRU | INT8 정적 | 170 | 18.81 | 15.29 | +0.33 | 1.68 | 6.4 | **216.8** | 0.6% |
| LSTM | FP32 | 236 | 18.50 | 14.87 | - | - | - | - | - |
| LSTM | INT8 동적 | **68** | 18.58 | 14.96 | +0.09 | 0.88 | 6.0 | 36.8 | 0.8% |
| LSTM | INT8 정적 | 222 | 18.73 | 15.27 | +0.40 | 1.58 | 6.3 | **210.8** | 0.6% |
| TCN | FP32 | 188 | 19.66 | 15.60 | - | - | - | - | - |
| TCN | INT8 동적(QUInt8) | **56** | 20.06 | 15.97 | +0.37 | 1.36 | 10.8 | 29.8 | 5.1% |
| TCN | INT8 정적 | **62** | 19.63 | 15.92 | +0.31 | 1.90 | 8.8 | **179.2** | 2.2% |

(차이는 12칸 예측 전체 CO₂ 에 대해 FP32 출력과 비교. 과제 7 원래 기준인 'ONNX 변환 오차 1ppm 이하'와 같은 잣대로 보면 INT8 은 모두 기준을 넘는다.)

- **평균은 괜찮다**: 시험 MAE 가 0.1~0.4ppm(1~3%) 나빠질 뿐이다. 왜 → 작은 오차가 대부분 샘플에서 상쇄되고, 원래 예측 오차(15ppm)에 비해 작다.
- **최대 차이는 위험하다 (특히 정적)**: 정적 INT8 의 최대 차이 180~217ppm 은 세 모델 모두 **같은 샘플(라운지 10/12 12:50)** 에서 나왔다. 왜 → 정적 방식은 검증 주 입력 범위(정규화 값 −1.98~5.85)로 잘라 두는데, 시험 주에는 그 밖의 값(−4.45~7.75)이 나와 **잘림(포화)** 이 생긴다. 동적 방식은 실행 때마다 범위를 다시 재서 이 문제가 작다(최대 11~37ppm).
- 그래서: 실데이터처럼 처음 보는 값이 나올 수 있는 환경에서 정적 INT8 을 쓰려면 보정 데이터를 넓히거나(여러 주·계절), 입력을 미리 클리핑해야 한다. 알람(850ppm 등 임계값) 판단에 바로 쓰기에는 최대 차이 200ppm 은 받아들일 수 없다.

run2 도 모든 칸이 run1 과 ±10% 안 (예: TCN 정적 배치4 p50 0.118ms, FP32 0.324ms).

어제(10/21) FP32 측정(reports/bench_board_cpu.json)과 비교:
| 모델 | 10/21 FP32 배치1 평균 / p95 | 10/21 FP32 배치4 평균 / p95 | 오늘 FP32 배치4 평균 / p95 |
|:--|--:|--:|--:|
| GRU | 0.22 / 0.22 | 1.01 / 4.52 | 0.50 / 0.52 |
| LSTM | 0.48 / 4.26 | 0.64 / 4.32 | 0.30 / 0.33 |
| TCN | 0.26 / 0.15 | 0.79 / 4.41 | 0.33 / 0.34 |

- **어제와 오늘 FP32 가 다르다**: 어제는 다른 팀원의 작업이 돌던 때라 p95 가 4ms 대로 튀었고, 오늘은 보드가 한가해(load 0.1) p95 ≈ 평균이다. 그래서 INT8 비교는 **같은 시각에 같이 잰 오늘 FP32** 와 해야 공정하다.
- **INT8 이 빨라진 건 TCN 정적뿐**: Conv+Linear 가 모두 INT8 커널(QLinearConv)로 합쳐져 배치4 에서 2.8배 빨라졌다. GRU 는 INT8 이 된 부분이 끝단 Linear 뿐이라 양자화·역양자화 비용만 늘어 오히려 2~3% 느려졌고, TCN 동적은 매번 활성값 범위를 재는 비용(DynamicQuantizeLinear 6개) 때문에 19% 느려졌다.
- 그래서: 지금 모델은 FP32 로도 0.1~0.5ms 라 매분 주기(60,000ms)에 비해 이미 충분히 빠르다. **INT8 의 실익은 '속도'보다 '파일 크기'(LSTM·TCN 1/3~1/4)** 이며, 정확도 위험(정적의 포화)을 감수할 이유가 작다. 서비스 기본은 FP32 ONNX 를 유지하고, 공간 수가 크게 늘어 CPU 가 모자라면 TCN 정적 INT8(보정 데이터 보강 후)을 후보로 둔다.

## 4. TensorRT INT8 은 못 했다
- 보드에 **CUDA 툴킷·TensorRT 가 없다** (`/usr/local/cuda*` 없음, `dpkg -l | grep tensorrt` 0건, `import tensorrt` 실패). ONNX Runtime 제공자도 Azure·CPU 두 개뿐이라 CUDA/TensorRT EP 를 쓸 수 없고, PyTorch 도 CPU 빌드(2.14.1+cpu)다.
- 설치는 JetPack 시스템 구성요소라 sudo·apt 가 필요한데, 팀 공용 보드이고 최근 두 번 멈춘 적이 있어 이번 작업 규칙(시스템 설치 금지)상 하지 않았다.
- 그래서: 위 INT8 결과는 모두 **CPU INT8** 이다. GPU INT8(TensorRT)은 팀 합의 후 JetPack 의 CUDA·TensorRT 를 설치하고 `trtexec --int8 --calib` (보정은 같은 검증 주 512샘플)로 다시 재야 한다. GRU/LSTM 은 TensorRT 에서도 RNN 층이 INT8 지원이 제한적이라 효과는 TCN 에서 가장 클 것으로 예상한다(측정 아님).

## 6. 로컬 LLM 과 같이 올릴 수 있는 조합 (계산)
가정 (실측 아님, 일반적인 llama.cpp 4-bit(Q4_K_M) 기준): **3B ≈ 2.0~2.5GB**, **7B ≈ 4.0~5.0GB** (가중치 + 짧은 문맥 KV 캐시 + 실행 버퍼). Jetson 은 CPU·GPU 가 같은 7.5GB 를 나눠 쓰므로 GPU 로 돌려도 같은 메모리에서 빠진다. 스왑이 0 이라 넘치면 느려지는 게 아니라 **프로세스가 죽거나 보드가 멈춘다** → 여유 0.5GB 이상 남긴다.

**경우 A — 지금처럼 팀 공용 (실측 available 4,416MB, 다른 팀원 서비스·데스크톱 포함)**
| 조합 | 우리 스택 | LLM | 합계 | 남는 양 (4,416 − 합계) | 판단 |
|:--|--:|--:|--:|--:|:--|
| ONNX+sklearn + 3B | 170 | 2,000~2,500 | 2,170~2,670 | 1,750~2,250 | ✅ 여유 있음 |
| ONNX+sklearn+Chronos + 3B | 531 | 2,000~2,500 | 2,531~3,031 | 1,385~1,885 | ✅ 가능 |
| ONNX+sklearn + 7B | 170 | 4,000~5,000 | 4,170~5,170 | 246 ~ −754 | ❌ 여유 0.5GB 미만 또는 초과 |
| ONNX+sklearn+Chronos + 7B | 531 | 4,000~5,000 | 4,531~5,531 | −115 ~ −1,115 | ❌ 초과 |

**경우 B — 보드를 우리 서비스 전용으로 쓸 때 (추정: OS+데스크톱 약 1.5GB 를 빼면 쓸 수 있는 양 ≈ 7,485 − 1,500 = 약 6,000MB)**
| 조합 | 합계 | 남는 양 | 판단 |
|:--|--:|--:|:--|
| ONNX+sklearn + 7B | 4,170~5,170 | 830~1,830 | ⚠️ 가능하나 문맥을 짧게(2k 토큰 이하) |
| ONNX+sklearn+Chronos + 7B | 4,531~5,531 | 470~1,470 | ⚠️ 하한 쪽이면 여유 0.5GB 미만 — 권하지 않음 |
| ONNX+sklearn+Chronos + 3B | 2,531~3,031 | 약 3,000 | ✅ |

- **추천**: 상시 = **서비스 GRU ONNX + state_models (170MB) + 4-bit 3B LLM**. Chronos 는 필요할 때만 별도 프로세스로. 7B 는 보드를 전용으로 쓰고 Chronos 를 빼고 문맥을 짧게 할 때만.
- 이유: 공용 상태에서는 다른 팀원 프로세스(약 1.1GB: 다른 서비스 540MB·205MB, claude 340MB, 10:15 ps 기준)가 이미 있어 7B 를 올리면 여유가 거의 없다. 보드가 최근 두 번 멈춘 것도 스왑 없는 상태에서 메모리 압박이 원인일 가능성이 있다(확인은 못 함).
- INT8 로 우리 모델을 줄여도 아끼는 메모리는 1MB 미만이다(파일 0.2MB → 0.06MB). **메모리를 줄이려면 모델 양자화가 아니라 torch·sklearn 같은 라이브러리를 상시 프로세스에서 빼는 게 효과적이다.**

## 7. 못 한 것
- TensorRT INT8/FP16: CUDA·TensorRT 미설치(위 4절).
- AE 메모리: 저장된 AE 파일이 없음.
- LLM 메모리는 실제로 올려 보지 않은 일반적 추정치다(공용 보드에서 수 GB 를 올리면 다른 팀원 작업이 죽을 수 있어서).
- 실데이터(InfluxDB 8주)로 INT8 정확도는 재지 않았다 — 이번 과제 3 모델이 합성 데이터로 학습된 모델이기 때문.
