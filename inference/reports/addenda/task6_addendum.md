## 1. 심화: GRU + Chronos 앙상블 (같은 시점)

예측 = w·GRU + (1−w)·Chronos. w 는 0~1 을 0.05 간격으로 바꿔 **검증 60분 MAE** 가 가장 작은 값을 골랐다.

### 1-1. 합성 시험 주(5주차, 1,108개 시점) — CO₂ MAE (ppm)

| 방법 | 5분 | 15분 | 30분 | 60분 |
| --- | ---: | ---: | ---: | ---: |
| 현재값 유지 | 10.0 | 21.1 | 36.6 | 38.4 |
| GRU (일정 포함) | **5.9** | **8.3** | **12.3** | **14.8** |
| Chronos-Bolt tiny | 11.4 | 19.5 | 35.5 | 40.1 |
| 단순 평균 (GRU+Chronos)/2 | 7.6 | 12.3 | 20.9 | 24.0 |
| 검증으로 고른 가중 (w=1.00 → GRU 만) | 5.9 | 8.3 | 12.3 | 14.8 |
| GRU (일정 제외) | 7.5 | 13.3 | 18.1 | 19.9 |
| 단순 평균 (GRU 일정 제외 + Chronos)/2 | 8.3 | 14.8 | 23.6 | 25.8 |
| 검증으로 고른 가중 (w=0.90·GRU 일정 제외 + 0.10·Chronos) | 7.4 | 13.2 | 18.3 | **19.3** |

- 검증 60분 MAE: GRU 18.9 / Chronos 50.6 → 검증이 "Chronos 섞지 말 것(w=1)"을 골랐다. 두 모델 60분 오차 상관은 0.17 로 낮지만, Chronos 오차가 GRU 의 약 2.7배라 섞으면 손해다.
- 일정이 없는 GRU 와는 10%만 섞었을 때 19.9 → 19.3ppm (약 3%) 조금 좋아진다.
- **왜 그런가 → 그래서**: 평균은 "비슷하게 잘하는데 다른 곳에서 틀리는" 두 모델일 때만 이득이다. 합성처럼 직접 학습 모델이 훨씬 잘 맞는 곳에서는 앙상블을 하지 않는다(가중치는 반드시 검증으로 정하면 자동으로 이렇게 된다).

### 1-2. 내 수집 실데이터 (230개 시점) — CO₂ MAE (ppm)

**(가) 230개 전체, 고정 가중 0.5 (데이터로 고르지 않음 → 누수 없음)**

| 방법 | 5분 | 15분 | 30분 | 60분 |
| --- | ---: | ---: | ---: | ---: |
| 현재값 유지 | 8.0 | 15.1 | 24.9 | 42.0 |
| 실데이터 학습 GRU (서비스 모델) | 8.5 | 15.2 | 23.5 | 39.3 |
| Chronos-Bolt tiny | 10.0 | 15.0 | 22.1 | 36.0 |
| **단순 평균 (GRU+Chronos)/2** | 8.4 | **13.5** | **21.1** | **34.4** |

**(나) 앞 절반(10-20 17:50 ~ 10-21 05:25, 115개)에서 w 고르고 뒤 절반(05:25 ~ 15:55, 115개)에서 보고**

| 방법 (뒤 절반) | 5분 | 15분 | 30분 | 60분 |
| --- | ---: | ---: | ---: | ---: |
| 현재값 유지 | 9.7 | 20.9 | 36.4 | 62.0 |
| 실데이터 GRU | 10.9 | 21.5 | 36.7 | 64.3 |
| Chronos-Bolt tiny | 12.8 | 21.7 | 33.1 | **55.5** |
| 단순 평균 0.5 | 10.5 | **19.0** | **32.6** | 56.7 |
| 가중 w=0.60·GRU + 0.40·Chronos (앞 절반에서 고름) | 10.4 | 19.2 | 33.0 | 57.8 |

- 실데이터에서는 두 모델 실력이 비슷해(60분 39.3 vs 36.0) 단순 평균이 **34.4ppm 으로 둘 다보다 좋다** (Chronos 대비 −4.5%, 현재값 유지 대비 −18%). 다만 60분 오차 상관이 0.70 으로 높아 이득은 작다.
- 앞 절반(밤, CO₂ 가 거의 안 변함)에서 고른 w=0.6 은 뒤 절반(낮, 수업)에서 Chronos 단독보다 못했다(57.8 vs 55.5). 밤 구간은 낮의 검증이 되지 못한다.
- **왜 그런가 → 그래서**: 표본이 22시간·230개뿐이고 밤/낮 성격이 달라 "검증으로 가중치 고르기"가 아직 믿을 만하지 않다. 지금은 **고정 0.5 평균을 후보로 두고**, 낮 데이터가 1~2주 쌓이면 '지난주 낮'을 검증으로 w 를 다시 정한다. 추가 비용은 Chronos 한 번(보드 약 90ms)뿐이다.

## 2. 생각해 볼 점: "차이 중 시간대·요일·온습도·일정 몫" — GRU 입력 제거 실험 (합성)

같은 학습/검증/시험 분할, 같은 구조(GRU 2층 64), 최대 40 epoch · 조기 종료(검증 6회 연속 개선 없음) — 과제 3 과 같은 설정이다(**epoch 를 줄이지 않았다**). seed 2개(0, 1) 평균. 변수를 뺀 모델은 처음부터 다시 학습했다.

| 입력 | 5분 | 15분 | 30분 | **60분** | seed별 60분 | 검증 60분 |
| --- | ---: | ---: | ---: | ---: | --- | ---: |
| (a) 전체 (CO₂·온습도·시간대·요일·일정) | 5.9 | 8.6 | 12.8 | **15.5** | 14.8 / 16.1 | 18.9 |
| (b) 시간대·요일 제외 | 6.1 | 8.6 | 13.5 | 16.1 | 16.0 / 16.1 | 21.7 |
| (c) 온도·습도 제외 (CO₂ + 시간 + 일정) | 5.9 | 8.4 | 12.8 | 15.1 | 14.7 / 15.6 | 18.7 |
| (d) 일정 제외 (CO₂·온습도·시간대) | 7.8 | 14.1 | 18.2 | 21.0 | 20.6 / 21.4 | 27.0 |
| (e) CO₂ 과거값만 (Chronos 와 같은 정보) | 7.1 | 14.5 | 21.6 | 33.5 | 34.1 / 32.9 | 41.5 |
| 참고: Chronos-Bolt tiny (CO₂ 과거 24h, 학습 없음) | 11.4 | 19.5 | 35.5 | 40.1 | | 50.6 |
| 참고: 현재값 유지 | 10.0 | 21.1 | 36.6 | 38.4 | | |

(seed 0 의 (a)는 기존 `models/forecast_gru.pt` 결과 14.8 과 똑같이 재현됨.)

**Chronos(40.1) → 전체 GRU(15.5) 차이 24.6ppm 나누기** (위에서부터 차례로 정보를 더한 순서 기준)

| 단계 | 60분 MAE | 줄어든 양 | 몫 |
| --- | ---: | ---: | ---: |
| Chronos (같은 CO₂ 과거, 학습 없음) | 40.1 | | |
| → (e) 같은 정보로 **우리 데이터에 학습** | 33.5 | 6.6 | 27% |
| → (d) **시간대·요일 + 온습도** 추가 | 21.0 | 12.5 | 51% |
| → (a) **일정** 추가 | 15.5 | 5.5 | 22% |

- **온도·습도의 몫은 거의 0** 이다: (c) 빼도 15.1 로 오히려 같거나 조금 낫다. 그러니 (e)→(d) 의 12.5ppm 은 사실상 **시간대·요일** 몫이다.
- **시간대와 일정은 서로 대신한다**: 일정이 있으면 시간대를 빼도 +0.6ppm 뿐(b), 일정이 없으면 시간대가 12ppm 을 줄인다. 합성 시간표는 매주 똑같아서 '월요일 9시'가 곧 '수업 시작'이기 때문이다. 일정은 시간표가 바뀌는 날(휴강·보강·예약)에 시간대가 못 하는 몫을 더한다.
- **왜 그런가 → 그래서**: Chronos 가 지는 이유의 약 3/4 은 "언제 수업이 시작하는지 모른다"(시간대·일정)이고, 나머지 1/4 은 우리 교실 패턴을 배우지 않은 탓이다. 따라서 Chronos 를 쓴다면 **시간대·일정을 공변량으로 넣을 수 있는 모델**(3장)이 가장 효과가 클 것이고, 온습도는 넣을 필요가 낮다. 직접 학습 모델에서도 온습도 입력은 빼도 된다(입력·전처리 단순화).

## 3. 심화: 공변량을 받는 사전학습 모델 (Chronos-2)

**가능 여부 확인 결과**
- 저장소 `.venv` 는 Python 3.9 라 pip 로는 chronos-forecasting 1.5.3 까지만 보인다(Chronos-Bolt 만 지원). TimesFM 도 PyPI 에 1.0.0 만 보인다.
- 따로 Python 3.11 가상환경(uv)을 만들어 chronos-forecasting **2.3.2** 설치(약 2분, 805MB) + `amazon/chronos-2`(120M, 478MB) 내려받기(약 1.5분)까지는 **약 4분에 성공**했다. Chronos-2 는 과거 공변량(온습도)과 미래에 아는 공변량(일정·시간대)을 받는다.

**실행 결과 — 중단됨 (검증 구간 일부만 측정)**

| 검증 4주차 (1,228개 시점) 60분 CO₂ MAE | 60분 | 10~90% 적중률(60분) |
| --- | ---: | ---: |
| Chronos-Bolt tiny (참고, 같은 시점) | 50.6 | - |
| Chronos-2, CO₂ 만 | 48.8 | 76% |
| Chronos-2 + 온도·습도(과거) | 50.0 | 74% |
| **Chronos-2 + 일정(과거 + 미래 60분)** | **34.1** | 75% |
| GRU 전체 입력 (참고, 같은 시점) | 18.9 | - |

- **시간대·요일 공변량, 전부 넣은 조합, 시험 주(5주차) 측정은 하지 못했다.** 공유 MacBook 에서 메모리가 부족해져(Chronos-2 가 공변량 여러 개 × 수백 시점을 한꺼번에 처리하며 수 GB 사용, 다른 실험과 동시 실행) 사용자 앱이 강제 종료되는 일이 생겼고, 그래서 작업을 멈추고 별도 venv 도 지웠다. 위 값은 검증 구간 값이라 **시험 결과가 아니다** — 경향을 보는 참고로만 쓴다.
- 그래도 경향은 2장과 맞다: **일정을 넣으면 48.8 → 34.1ppm (−30%)**, 온습도는 효과 없음(오히려 +1.2). 다만 일정 공변량을 넣은 Chronos-2(34.1)도 직접 학습 GRU(18.9)보다 아직 훨씬 나쁘다.
- **다음에 할 것**: 메모리 여유가 있는 장비(또는 MacBook 을 비운 상태)에서 `addenda_task6_chronos2.py` 를 묶음 크기 32 정도로 줄여 다시 돌려, ① 시간대 공변량, ② 전부, ③ 시험 주 결과, ④ 실데이터(실습실 실제 시간표 공변량) 를 채운다. 보드에는 Python 3.12 가 있으므로 2.x 설치는 가능하지만, 아래 4장처럼 메모리가 Bolt-tiny 보다 크게 든다.

## 4. LLM 과 함께 올릴 때 메모리 예산 (Jetson Orin Nano Super 8GB)

### 4-1. 프로세스 메모리 (RSS, MB)

| 구성 (새 프로세스에서 불러오고 1회 추론) | MacBook RSS (3회) | 보드 RSS (task7 보강 측정) |
| --- | ---: | ---: |
| python + numpy/pandas (바탕) | 63 | 12 (python만) / 45 (+ORT·numpy) |
| + ONNX Runtime + GRU ONNX | 79 | 55~57 (GRU·LSTM·TCN ONNX 모두) |
| + AE ONNX + 상태 모델 pkl (sklearn) | 158~163 | 170 (pkl 포함, AE 파일은 저장돼 있지 않음) |
| torch import 만 | 187~209 | 355 (위 서비스 구성 + torch) |
| torch + Chronos-Bolt tiny | 331~374 | 480 (로드) → **531** (추론 5회 후) |
| torch + Chronos-Bolt small | 510~549 | (미측정) |
| torch + Chronos-2 (py3.11, 공변량 7개 1회) | 529~858 | (미측정) |

- Chronos-Bolt tiny 의 몫: MacBook 에서 torch 대비 +약 165MB, 보드에서 +125MB(로드) +51MB(추론) ≈ **+176MB**, 그리고 torch 자체가 +185MB. 기존 보고서의 "+68MB" 는 torch·다른 모델이 이미 올라온 뒤의 최대 RSS 증가분이라 **torch 비용이 빠진 값**이다. 서비스에 Chronos 를 새로 넣으면 실제로는 **약 +360MB**(torch + Chronos)로 봐야 한다.
- AE 는 가중치 약 6,800개(ONNX 약 28KB)라 메모리는 무시할 만하다. 서비스 쪽 비용의 대부분은 sklearn(pkl) 불러오기(+약 110MB)다.
- 보드 시스템 전체로는 Chronos 묶음을 띄우기 전후 `free -m` used 가 3,069 → 3,421MB (**+352MB**) 로 위 추정과 맞는다.

### 4-2. 계산 (보드 total 7,485MB = `free -m` 실측)

가정: 4bit 3B LLM 가중치+KV 캐시 2,000~2,500MB(요청서 값), LLM 실행기(llama.cpp/CUDA 문맥) 오버헤드 300~500MB(**가정, 미측정** — Jetson 은 CPU·GPU 가 메모리를 같이 씀), 안전 여유는 최소 1,000MB 를 남긴다.

| 항목 | 시나리오 A: 바탕 1.7GB (요청서) | 시나리오 B: 바탕 3.07GB (오늘 10:18 실측 used) |
| --- | ---: | ---: |
| 바탕 사용량 (OS·수집기·현재 서비스 등) | 1,700 | 3,069 |
| 예측 서비스 (ORT + GRU ONNX + AE + 상태 모델) | +170 | +170 |
| Chronos-Bolt tiny (torch 포함, 531 − 170) | +361 | +361 |
| 4bit 3B LLM (가중치+KV) | +2,000 ~ 2,500 | +2,000 ~ 2,500 |
| LLM 실행기 오버헤드 (가정) | +300 ~ 500 | +300 ~ 500 |
| **합계** | **4,531 ~ 5,231** | **5,900 ~ 6,600** |
| **남는 메모리 (7,485 − 합계)** | **2,954 ~ 2,254** | **1,585 ~ 885** |
| 판정 (여유 ≥ 1,000MB) | ✅ 넉넉 | ⚠️ 좋은 경우만 통과, 나쁜 경우(2.5GB LLM) 885MB 로 기준 미달 |

- 시나리오 B 의 바탕 3,069MB 에는 현재 서비스(170MB)가 이미 들어 있을 수 있어 실제로는 약 170MB 더 여유가 있을 수 있다(그래도 나쁜 경우 약 1,050MB 로 기준선에 걸림).
- Chronos 를 빼고 GRU ONNX 만 쓰면 361MB 를 아낀다 → 시나리오 B 나쁜 경우도 1,246MB 남아 통과. Chronos-2 를 쓰면 MacBook 기준 Bolt-tiny 보다 +200~500MB 더 들어 시나리오 B 에서는 넘친다.
- **왜 그런가 → 그래서**: 8GB 를 CPU·GPU 가 같이 쓰므로 LLM 이 가장 큰 몫(약 1/3)을 차지한다. 다른 팀원 작업이 함께 도는 날(시나리오 B)을 기준으로 잡아, ① 상시 예측은 **GRU ONNX(torch 없음)** 로 두고, ② Chronos-Bolt tiny 는 앙상블 이득(실데이터 −4.5%)이 확인되면 별도 프로세스로 켜되 메모리가 부족하면 끄는 예비 기능으로 둔다, ③ LLM 은 KV 캐시(문맥 길이)를 줄여 2GB 안쪽으로 맞춘다. 보드에서 LLM 을 실제로 띄운 뒤 `free -m`/tegrastats 로 위 표를 다시 채운다.

## 못 한 것 / 주의

- Chronos-2: 검증 구간 3개 조합만 측정, 시험 구간·시간대 공변량·실데이터는 못 함(메모리 문제로 중단, 위 3장).
- LLM 오버헤드(300~500MB)는 가정이다. 보드에서 LLM 을 함께 띄운 측정은 하지 않았다.
- 실데이터 앙상블은 22시간·230개 시점이라 표본이 작다. 차이 1~2ppm 은 우연일 수 있다.
- 입력 제거 실험은 합성 데이터에서만 했다(합성 시간표는 매주 같아 시간대의 몫이 실제보다 크게 나왔을 수 있다).
